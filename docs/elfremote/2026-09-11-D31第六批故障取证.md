### 紧凑索引合同

回执字段为`schemaVersion=1`、`kind=FAULT_PENDING_INDEX`、`events`、`total`、`hasMore`、`nextAfter`、`capacity`、`verificationScope=METADATA_ONLY`、`selection=ALL_RETAINED_HOST_SELECTS_PENDING`、`pagination=LIVE_ID_ORDER_RESTART_FROM_EMPTY_EACH_SWEEP`、`rawContentInSummary=false`、`uploadState=LOCAL_ONLY`。

每个事件仅包含六项：

| 字段 | 含义及值 |
| --- | --- |
| `eventId` | 冻结来源的事件摘要 |
| `category` | `ANR/TOMBSTONE/DROPBOX/BOOT`；损坏时可能为`UNKNOWN` |
| `phase` | `PENDING/CAPTURING/RETRY_WAIT/CAPACITY_BLOCKED/AWAITING_POST/COMPLETE/PARTIAL`；损坏为`INDEX_CORRUPT`，无法识别为`UNKNOWN` |
| `captureState` | 原状态元数据中的`COMPLETE/PARTIAL`或`UNKNOWN`；本次不读原件证明完整性 |
| `exportState` | `NOT_EXPORTED/INCOMPLETE_EXPORT/RECEIPT_RECORDED_UNVERIFIED/UNKNOWN` |
| `archiveState` | `NOT_ACKNOWLEDGED/ACK_RECORDED_UNVERIFIED/INVALID_RECORD/UNKNOWN` |

虽然命令名为`pending`，它分页列出全部保留事件，包括已记录归档确认者，不依据未核验标记静默隐藏事件。宿主选择终态`COMPLETE/PARTIAL`作为可导出候选；`captureState=PARTIAL`仍可导出已有证据，但不能称完整源。损坏事件保持可见，不能当作成功或不存在。已确认记录仍须与宿主持久验包证据关联，不能仅凭`ACK_RECORDED_UNVERIFIED`认定下载成功或永久放弃待办。

紧凑查询只读有界JSON，不读取ZIP或原始日志，不触发摘要缓存、采集、导出或归档。`RECEIPT_RECORDED_UNVERIFIED`与`ACK_RECORDED_UNVERIFIED`仅是记录存在且事件ID/状态相符，故意不伪装成完整核验。实际`export/archive`仍按第五批合同全量核对包、清单及冻结原件。

按ID升序分页，`nextAfter`为本页最后ID；空页返回空游标，`hasMore=false`。这不是冻结快照：一轮中较小ID的新事件可能已落在游标后方，因此每轮必须从空游标重新开始，宿主按事件/导出身份去重；不能永久持有最后ID作为增量日志游标。最多128个保留事件，每页16项时静态集合最多8页。

`capacity.scope=LAST_SCAN_NOT_LIVE`，其它字段为最近扫描的`state/capturedAtMs/activeEvents/archivedEvents/retainedEvents/retainedBytes/maxActiveEvents/maxRetainedEvents/maxArchiveBytes/eventIndexErrors/admissionBlockedBy`。缺失数值为`-1`，状态为`UNKNOWN`，不能补作零。归档后到下一次扫描之间统计可能仍旧，事件的确认记录与统计时间应分开理解。

新增准入原因采用固定枚举：`ACTIVE_EVENT_LIMIT`、`RETAINED_EVENT_LIMIT`、`ACTIVE_RESERVATION_LIMIT`、`ARCHIVE_BYTE_LIMIT`、`FREE_SPACE_RESERVE`。32活跃但总字节尚有余额时，不再需要把泛容量状态猜成磁盘满。旧108扫描记录无此数组时不能据空数组宣称无限制。

`FaultExports.MAX_EXPORTS=2`保持不变，紧凑查询直接引用这个常量。宿主回执校验也必须限制`exportNumber`为1或2，不能因已有代码允许3就扩大设备导出重试上限。

## 目录发现与公平推进

生产`FaultDirectoryWalker.Android`仍使用已存在的`/system/bin/busybox find`，不经shell，不接收请求中的可执行文件或目录。只读打开固定来源目录，核对实际设备号、inode、长度、时间、权限及属主，将其文件描述符固定后传给子进程`/proc/<父进程>/fd/<描述符>/.`。枚举只到一层、使用`-print0`；每条返回记录必须严格匹配这个实际前缀，UTF-8损坏、路径分隔符或越界子名明确拒绝。结束时再次核对固定目录身份和原路径。没有持续保留的find进程，结束、超限或异常均销毁子进程并关闭流及描述符。

不再把最先收到的64个目录名字作为全部候选。流式处理全部预算内名称，无关名称不占候选名额；只有匹配原白名单的普通文件才参与候选选择。每源内存保留按mtime最新的32项，加上按名称游标轮转的32项积压候选，重叠去重，最多64项；排序不依赖目录枚举顺序。mtime仍是文件时间，不声称为真实崩溃发生时间。

最新集合与积压页交错执行身份摘要读取，避免最新集合独占读取预算。积压游标只推进到本轮实际尝试身份读取的连续页项，放在已有`schedule.json`的`discovery`字段，核心或独立命令进程重建后恢复，不增加故障根目录文件。后续源状态仍以当前stat和前4096字节摘要重新确认，不把名称游标当作完整内容身份。

默认四个来源各分得最多1250毫秒，总发现预算仍为5秒；约三分之二用于目录/元数据，余下用于选中原件的身份读取。单源最多处理4MiB目录输出，单条名字记录最多8192字节；整个目录不进入Java数组，也不常驻logcat。单源超时不会把正常剩余来源的时间份额提前耗尽。

覆盖回执增加`enumerationComplete/nonemptyEnumeration/enumerated/matched/selection/sourceBudgetMs`，并保留`accepted/unreadable/state/reason`。目录完整枚举与全部源已取得身份是不同事情，超过64候选时即使枚举完成仍为`PARTIAL / CANDIDATE_PAGE_OR_READ_LIMIT`。

明确边界：流式枚举仍受时间与4MiB输出限制；触限、目录持续变化、权限拒绝、底层IO迟滞或源在采集前被清理时，不保证全目录最新项已发现。游标只轮转已枚举到的匹配候选，不能越过反复因时间/字节限制而从未读到的目录部分。这里解决的是固定前64名字导致的遗漏，不宣称任意大目录均可穷尽；`enumerationComplete=false`必须作为持续覆盖缺口保留。预算是合作式检查，不能冒充所有内核IO的强制实时截止。

采集调度先去掉已有事件的观察项，再对新候选按来源轮转，每源内部优先mtime新的候选。新来源先使用约半数本轮工作名额，另一部分公平推进已有未完成事件，余量回给新来源；只有一个名额时交替给新旧事件。来源轮转位置由实际最后接纳来源推进，旧事件使用持久ID游标，进程重建不重置公平性。已有记录、已封存及已归档来源仍参与去重，不成为新故障，也不覆盖冻结原件。

默认32活跃、128保留、64MiB总字节、32MiB可用空间预留与每源最多3次采集保持。归档只释放活跃槽位，不删除原件、不释放字节，ZIP和失败残留继续计入总量。新源不能挤掉旧原件，达到任一准入上限仍停止新增；只有确实存在名额和磁盘预算时才能继续。公平性不是容量豁免，也不是完整自动补传能力。

## 110实际枚举失败与112局部修正

主任务提供的真实回执`research/d31/captures/2026-09-11/parallel-batch6-discovery-web110/01-parsed-private.json`记录四类来源均为`UNAVAILABLE / UNSTABLE_DIRECTORY`、`candidateCount=0`、探针总状态`PARTIAL`。本线只读核对原件与生产调用图，确认失败发生在固定目录描述符的首次身份比较，尚未启动BusyBox枚举；不能把110该次结果解释为已验证find前缀，也不能解释为四个源目录同时真实变化。

根因为字段表示不一致：共享`AndroidCollectionAccess.stat(StructStat)`将文件类型分离到`Stat.type`，将`mode`保存为`st_mode & 07777`，而新枚举器把该权限字段与包含`S_IFDIR`类型位的原始`fstat.st_mode`直接比较。例如权限`0700`与原始目录模式`0040700`不能相等。旧桌面枚举夹具没有执行Android目录打开及这次比较，因此先前74项离线通过没有覆盖这个生产映射缺陷。
