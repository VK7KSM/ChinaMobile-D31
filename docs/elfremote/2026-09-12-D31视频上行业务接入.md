## 复用方式与公共接口

相机链复用D22既有的 `Camera1Enumerator(false)`、`SurfaceTextureHelper`、`VideoSource`、`VideoTrack` 和 `SEND_ONLY` 轨道。固定WebRTC依赖为 `io.github.webrtc-sdk:android:125.6422.07`。编码器按实际支持列表优先H264，保留VP8等回退；没有据此宣称D31硬件H264编码已验证。

组件借用主线现有Peer和factory，不另建Peer、不建立上传队列、不创建本地录像。音频仍由主线既有RTC链负责；视频组件自身不创建音频或改变音量、扬声器路由。

```java
new RtcVideoEncoding(Context app) throws Exception;
VideoEncoderFactory encoderFactory();
VideoDecoderFactory decoderFactory();
EglBase.Context context();
void close();

new RtcVideoCapture(
    Context app, PeerConnectionFactory factory,
    PeerConnection peer, RtcVideoEncoding encoding,
    String requestedFacing, boolean verifiedUnmetered,
    RtcVideoCapture.Changed changed);

void start() throws IOException;
```

`Changed.changed(JSONObject)`仅在状态变化时通知，不逐帧触发云上报。`start()`和`close()`不等待相机释放；两个等待方法只允许媒体工作线程调用。EGL构造按需在媒体工作线程执行，不放入开机初始化或周期报告。

## 与主线的最终接线

以下是已读取源码确认的接线状态，不是142运行结果：

1. `media/RtcOffer.java`与`media/AppMediaContract.java`接受既有 `video` 模式及 `front/back` 相机选择，继续使用原会话校验。
2. `media/AppMediaBackend.java`通过原APP身份、已有控制器和媒体占用保护创建会话，将Offer传入 `AndroidRtcMicrophone`；没有新增第二套APP服务。
3. `media/AndroidRtcMicrophone.java`创建factory前加入视频编码、解码工厂，创建Peer后启动视频，等待有效首帧；发布SDP时分别检查一个音频轨道和一个视频轨道，并使用实际轨道的 `mid`。
4. `media/MicrophoneSession.java`继续复用原RTC协商流程。就绪要求发布完成、ICE连通及 `captureReady()`，后者在视频模式额外要求 `video.ready()`。100毫秒健康检查调用 `Peer.requireHealthy()`，在会话已进入传输状态后仍能消费视频失败。
5. `RemoteMediaSessions.java`负责视频可用性检查、会话分派及筛选后的诊断结果；`RemoteMediaReport.java`合并 `managed_media_modes`，视频能力同时要求媒体侧可用及已有相机数量缓存大于零；`RemoteDaemon.java`将视频Offer交给现有媒体会话，避免与视觉拍照会话并发。
6. 继续使用已有WebRTC传输、网页录制及分段上传路径，没有新增上传接口。此前Web合同审查指出完整视频录制需要音频和视频轨道；仅验证无音频画面不能作为完整录像验收。

## 单摄像头、超时与资源释放

此前D31只读记录报告一个后置摄像头、方向值0。本组件只在摄像头总数为1时允许默认前置请求回退到唯一摄像头，并报告实际朝向。多摄像头设备必须匹配请求，不任意回退。

已确认不计量网络采用640×480、15帧、600000比特；计量或未知网络采用320×240、10帧、180000比特。主线提供网络判断，组件不另行轮询网络。

- 就绪要求轨道已挂接、采集启动回调成功、有效首帧已送入视频源；不把创建轨道成功当作录像开始。
- 10秒内没有首帧则失败关闭；连续5秒没有新的有效帧时间戳则停止，重复或倒退时间戳不能续期。
- 相机锁复用APP规范化私有目录下的 `visual-photo/media.lock`，与静态拍照互斥。
- 关闭立即取消转发，实际清理在采集工作线程执行；3秒未确认释放则报告未确认，不能把锁当作已释放。
- 固定WebRTC字节码表明 `CameraCapturer.stopCapture()`只是投递相机停止任务。组件在相机线程追加FIFO屏障并等待，确认已投递停止任务完成后才销毁相关对象。
- 主线先停止录音并关闭视频，确认视频释放后再依序关闭Peer、轨道、源、factory、音频模块及EGL。任一依赖释放失败立即停止后续销毁，仅成功后清空相应引用；观察器独立关闭。
- `MicrophoneSession.awaitClosed()`表示清理尝试结束，最终成功还必须检查 `cleanup_complete`，不能仅凭等待返回真判定资源全部释放。

## 本轮审核与修复

### 回调锁顺序修复

早期接线在视频组件持锁回调中同步执行 `events.failed()`，而会话快照持会话锁读取视频状态，存在反向加锁。主线已将回调改为仅写 `volatile videoFailure`，由既有100毫秒检查通过 `requireHealthy()`消费。最终只读复核确认此处不再同步进入会话锁，旧问题已关闭。

### 三处后续修复

| 问题 | 主线最终修复 | 复核结论 |
| --- | --- | --- |
| 停止录音抛异常会跳过视频关闭 | `setAudioRecording(false)`单独捕获异常，之后仍执行 `video.close()`及释放等待 | 当前控制流已落实 |
| Peer或factory释放失败后继续销毁EGL并清空引用 | 原生依赖放入同一顺序清理块，异常立即停止后续步骤，仅释放成功才置空；观察器单独清理 | 相机未确认或依赖释放失败时保留仍可能被使用的对象 |
| 启动具体错误被通用协商失败替代，清理错误丢失 | `publish()`复用 `failureCode()`；会话业务 `reason` 与 `cleanup_reason`分别保存 | 启动原因与清理原因不再混为一个字段 |

已读取主线新增测试 `MicrophoneSessionTest.asynchronousVideoFailureStopsWithoutCallingSessionUnderCameraLock` 和 `startupAndCleanupKeepSeparateSpecificCausesAndUnreleasedLock`。前者验证健康检查消费视频错误；后者验证首帧超时与释放未确认分别保存，并保持媒体锁。前者使用模拟Peer，并不等价于真实相机回调并发压力测试。此次快速复核只审查这些测试的源码，没有独立执行主线新增回归，其执行结果等待主线追加。

### 固定依赖确认的根因路径

对固定WebRTC类库的实际字节码重新核对，确认以下控制流：

1. `PeerConnection.addTransceiver()`将返回的包装对象加入本地 `transceivers` 列表。
2. 主线发布SDP调用 `getTransceivers()`，该方法先逐项 `dispose()` 原列表，之后才调用 `nativeGetTransceivers()`。
3. `RtpTransceiver.dispose()`调用其 `cachedSender.dispose()`；`RtpSender.dispose()`最终把本地原生句柄置零。
4. 142视频组件跨上述调用保存了旧sender。退出时调用旧sender的 `setTrack(null,false)`，首先进入 `checkRtpSenderExists()`，遇到零句柄直接抛出 `IllegalStateException`，原文为 `RtpSender has been disposed.`，尚未进入 `nativeSetTrack`。
5. `PeerConnection.removeTrack()`本身取得sender原生句柄后调用 `nativeRemoveTrack`，其Java实现不负责dispose sender。不能把包装对象失效归因于该方法隐含的双重dispose。

这是由固定依赖与142实际调用顺序确认的代码缺陷，不是根据通用错误码猜测相机性能。现场没有具体异常栈的限制仍成立。完整字节码保存在新证据目录的 `checks-1/sender-bytecode.txt`。

### 144组件修改与失败诊断

只修改正式 `media/AndroidRtcVideoCapture.java`，新增 `media/AndroidRtcVideoReleaseTest.java` 测试；没有修改主线共享接线或其他冻结代码。

- 启动只保存稳定sender ID；关闭时只调用一次 `getSenders()`，立即按原ID匹配当前包装并 `removeTrack()`，不跨调用保存新wrapper。
