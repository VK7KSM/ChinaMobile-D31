# D31第五批轨迹数据：定位缓存权限取证

## 2026-09-11：只读helper及离线合同交付

本轮目标是确认完整106的`permission_denied`发生在何处，不主动定位、不扫描Wi-Fi、不修改权限、UID、AppOps或定位开关。公共`RemoteDaemon/RemoteTelemetry`及生产采集入口保持不变；设备操作、安装与公共接线由主任务负责。本线未操作设备或运行Gradle。

### 事实与待证原因

主任务此前提供的真机结果是定位字段缺失、原因`permission_denied`。现有`AndroidTelemetryAccess.location()`把同一provider的`getProvider()`、`isProviderEnabled()`及`getLastKnownLocation()`放在同一个异常捕获块中；因此该结果不能确定失败发生在权限检查、包名归属检查，还是实际缓存读取。

第四批电池故障已经确认与未登记的应用线程有关，但不能直接推断定位采用相同机制。Android6定位服务没有“将应用线程设为空即可读取”的同等合同。

只读核对的AOSP基线是`android-6.0.1_r81`：

- [LocationManager.java](https://android.googlesource.com/platform/frameworks/base/+/android-6.0.1_r81/location/java/android/location/LocationManager.java)：`getLastKnownLocation(provider)`实际构造`LocationRequest.createFromDeprecatedProvider(provider,0,0,true)`，调用`getLastLocation(request,mContext.getPackageName())`。该请求对象仅作为缓存查询参数，不注册定位监听。
- [LocationManagerService.java](https://android.googlesource.com/platform/frameworks/base/+/android-6.0.1_r81/services/core/java/com/android/server/LocationManagerService.java)：`getLastLocation()`先取得调用者定位分辨率权限，再执行`checkPackageName()`及provider权限检查，随后仍有AppOps、黑名单、用户设置与缓存存在门。
- 同文件的`checkPackageName()`严格要求包名出现在`getPackagesForUid(Binder.getCallingUid())`中。空包名、没有包的UID、包与UID不匹配均可抛`SecurityException`；不能凭`Context.checkPermission()`返回通过就认为完整定位合同通过。
- `getProviderProperties()`本身也会检查定位权限。因此在`getProvider()`处失败时，现有生产代码可能尚未执行缓存读取。

这是AOSP合同依据，不是D31定制固件已经返回相同异常的证明。最可能的待证分支是独立root进程的UID与系统Context包名归属不匹配；需要下面helper的真实结果才能确定。不能把参数替换成已安装客户端或其它系统包名，更不能用权限修改、身份切换或伪造位置绕过检查。

### 实际记录内容

| 类别 | 证据与判断边界 |
| --- | --- |
| 身份 | 真实进程UID/PID、Binder调用UID/PID、SDK、Context类、真实包名与操作包名。 |
| 包归属 | PackageManager实读当前UID对应包、当前Context包的实际UID，区分`UID_PACKAGE_MATCH/UID_PACKAGE_MISMATCH/UID_HAS_NO_PACKAGES`。包查询失败单独记录，不当作没有包。 |
| 权限 | 精确记录fine/coarse针对实际进程及真实包名的查询返回值。查询通过不替代后续Binder成功。 |
| 服务 | 定位服务描述符及真实`getLastLocation/getProviderProperties/isProviderEnabled`方法签名。只按API23已确认的`getLastLocation(LocationRequest,String)`调用，不枚举尝试其它签名。 |
| 两个provider | 分别独立执行`getProvider`、`isProviderEnabled`、`getLastKnownLocation`与直接Binder缓存读取。前一步失败仍单独记录后续只读步骤，不再把属性失败误归为已读缓存。 |
| 异常 | 保存异常类型、消息和调用栈；最多4层原因链、每层12帧、每条消息2048字符，超过限制显式标记截断。反射调用展开真实目标异常，Binder拒绝不转换为空缓存。 |
| 缓存 | 保留`cache_returned`与`usable`两个独立判断；记录真实provider、原始精度、精度是否报告、模拟标志、原始墙钟与单调采样时间、观察时间和拒绝原因。使用现有5分钟年龄门，不截断精度或重写时间。 |

`cache_returned=false`只表示该次服务调用没有返回Location；仍可能是设置、AppOps或无缓存等原因，不能一律写成“设备没有GPS”。有Location但过期时为`cache_returned=true,usable=false`，不能用新报告时间把它变成新位置。

需要主任务回传的最短证据是helper JSON和stderr；不需要经纬度、全部系统日志、完整包清单或全设备扫描。结果可能包含必要的进程身份及错误信息，应放主任务私有证据目录，公开文档只摘录脱敏后的类型和结论。

### 结果判读与修复门

1. 若fine/coarse进程权限通过，但`uid_packages`表明真实Context包不属于调用UID，且缓存调用明确抛相应UID/包名异常，可确认身份合同失败。直接Binder并不改变调用UID，不能将相同参数的再次失败当作新的权限修复。
2. 若`getProvider`先拒绝、缓存方法独立调用却成功，需要按真实失败点最小调整生产读取顺序，并保持定位开关和新鲜度检查。
3. 若框架方法隐藏了RemoteException，而直接Binder记录服务异常，按服务失败处理；不能假造空缓存或授予权限。
4. 若同身份的两条缓存读取均成功返回空值，仅说明本次无返回位置；本批禁止为了取得非空值主动定位或扫描Wi-Fi。
5. 若确实需要由AMS登记的应用UID读取，应由主任务评估现有应用进程的只读桥接，而不是在本包内冒用身份。此类接线尚未实现，也不在本次helper交付中宣称完成。

生产缓存采集目前未作基于假设的权限绕过或身份修正；待真实证据收敛后再决定最小修复。既有来源、误差、模拟位置、单调时间和过期检查保持不变。

## 2026-09-11：依据106真机证据实现应用缓存桥，交108组合验收

### 已确认原因

主任务真实只读证据位于`research/d31/captures/2026-09-11/parallel-batch5-location-read106/output-private.txt`，本线仅读取该文件，没有操作设备。

### 生产修正与真实调用身份

已新增`AppLocationCache`、`AppLocationCacheContract`和`LocationCacheService`。`AndroidTelemetryAccess.location()`在API23、真实UID0、零主动采样窗口时自动调用应用缓存桥；公共构造方法、`TelemetryCollector.collect()`、`Sample.mergeReport()`均保持不变。电池仍沿用第四批已实现的只读粘性广播路径。

root只负责启动明确组件及接收结果；实际`getLastKnownLocation`由AMS正常登记的Service工作线程使用自己的应用Context调用。因此定位Binder看到实际应用UID及其所属包，不通过假包名、修改UID、修改权限或清除调用身份绕过检查。

AOSP6的`IActivityManager.startService(IApplicationThread,Intent,String,String,int)`明确拒绝null callingPackage。实现采用真实root Binder身份、空应用线程、明确Intent、空resolvedType、空字符串callingPackage及user0；空字符串表示root无所属包，没有传`android`、shell或目标客户端作为root的调用包。早期口头拟议的null callingPackage不适用，已经在实现前依据AMS源码更正。该API与不导出组件的实际启动仍须由主任务在D31验收。

返回使用一次性`ResultReceiver`，没有新文件队列。root端使用null Handler保留Binder线程上的真实发送UID，并与PackageManager查询的应用UID比较；同时核对随机请求编号、双方独立读取的真实`/proc/sys/kernel/random/boot_id`、请求开始与响应完成单调时间、协议版本及正文尺寸。不会把服务启动成功当作定位成功。

应用返回原始provider、精度、模拟标志、墙钟和单调采样时间；root重新执行现有来源、误差和缓存年龄校验。应用端读到过期或无效缓存时保留原始fix交校验，不再与“未返回缓存”混为一谈；只有通过新鲜度门的真实缓存可以进入报告。未知来源、模拟位置、未来时间或过期结果均不能补成新GPS。
