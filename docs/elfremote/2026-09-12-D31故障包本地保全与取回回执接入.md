# D31故障包本地保全与取回回执接入

## 2026-09-12 合同核对及修改范围

本子任务只修改 `research/d31_adb_bootstrap/tools/fault-transfer` 中的宿主模块及测试，并新建本记录。没有修改 Java、Daemon、主脚本或共享 Web，也没有发送生产回执或操作设备。

核对依据为 Web 的 `elfRemote/2026-09-12-R2版本保留与传输暂存清理.md`、`file-return.js` 的 `received` 分支及 `fault-client.js` 的本地验包调用顺序。接口是管理员会话鉴权的 `POST /api/elfremote/file-return/received?device_id=...&task_id=...`，正文只包含原文件的 `size` 与 `sha256`。服务端先记录 `delivered`，再清理 R2；`{ok:true,purged:true}` 与 `{ok:true,cleanup_pending:true}` 均为已接受回执。后一状态不代表本机失败，删除重试由服务端负责。

## 已实现流程

1. 沿原任务下载故障包，写入流完成、文件同步关闭后，核对外层长度和摘要。
2. 运行原 Python 逐项验包器，校验 ZIP 清单及每项内容，写入并同步验证记录。
3. 本机恢复状态持久保存为已保全，再建立包含原设备、原任务、长度和摘要的独立回执意图并持久化。
4. 发送前再次从磁盘核验原件和验证记录；调用新管理员接口，不携带设备令牌。
5. 成功将本机回执状态记为 `DELIVERED`，分别记录已清理或待服务端清理。失败保留 `PENDING`、错误代码和下一允许重试时间；原文件、验证记录和已保全状态保持不变。

每轮同一事件最多发送一次回执，遵守现有总请求预算、超时及服务端 `Retry-After`。响应未知或发送后宿主崩溃时，下一轮沿同一个原任务与原摘要重试幂等回执，不重新取包，也不依赖云副本仍存在。错误身份、未验包、写入失败、恢复状态保存失败、原件被修改时不发送回执。

## 宿主接线及归档边界

- `runRound` 原调用默认完成本机保全及取回回执，然后保持等待设备归档；不再自动运行 `FaultCommand archive`。
- 设备归档仍沿原核验、原任务及独立查询闭环，但必须显式传入 `archive:true`，CLI 对应 `--archive`。取回回执不是设备归档，也不代表完整事故窗口或已找到根因。
- `receiptsOnly:true`／`--receipts-only` 只读取已有保全目录并重试回执。不检查设备在线状态或当前版本，不派发任务，不重新下载，不执行归档。沿该目录原目标参数使用即可；目录中的原设备和任务绑定仍须核对。不能与发现模式或归档模式同时使用。
- 汇总新增 `preserved`、`awaitingArchive`、`deliveryPending`、`delivered`；`archived` 继续只表示设备归档已独立确认。回执失败不把已保全计数清零，也不将该事件改为本机失败。

## 测试发现的独立缺陷

已在 `PackageVerifier.mjs` 的调用边界使用 Windows 扩展长度路径，仍调用原验包器，不改变 ZIP、原件或验证规则。后续测试结果另行追加。
