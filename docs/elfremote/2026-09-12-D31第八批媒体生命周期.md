## 文件及实际接口

源码根为`research/d31_adb_bootstrap/`，本批新增四个文件，没有修改旧媒体或旧解析器文件：

- `app/src/main/java/net/elfradio/d31bootstrap/media/AudioCaptureLifecycle.java`。
- `app/src/main/java/net/elfradio/d31bootstrap/media/AudioCaptureLifecycleSession.java`。
- `app/src/test/java/net/elfradio/d31bootstrap/media/AudioCaptureLifecycleTest.java`。
- `app/src/test/java/net/elfradio/d31bootstrap/media/AudioCaptureLifecycleSessionTest.java`。

`AudioCaptureLifecycle(Identity, requestId, sessionId, Clock)`固定本次身份和请求。`Identity`包含固定APP包名、活动APK摘要、启动标识、UID、PID及实际音频session；`Clock.elapsed()`必须来自设备当前单调时钟。身份必须由可信APP/PackageManager及本次`AudioRecord`实读，不能采用Web自报值。构造参数校验不是身份认证，Flinger本身也不提供APK、启动标识或UID证明。

`Evidence`组合两份完整`AudioInputOwnership.Dump`、本次身份/请求/会话、其它音频因素的`External`状态及其独立单调起止。`External`只覆盖蜂窝、SIP、播放、焦点等非本次输入因素；缺来源、读取失败或无法排除其它占用必须为`UNKNOWN`。本批没有通过从原全局BUSY结果扣掉自己来伪造这项证据。

核心方法为`begin(Evidence)`、`started()`、`startFailed()`、`observe(Evidence)`、`snapshot()`、`requestStop()`、`cancelRequest(id)`、`confirmRelease(Release)`和`releaseFailed()`。它不访问设备、不创建线程。`Snapshot.continuationEligible`只表示当前离线规则满足，不授予现有guard豁免，不构成原子资源预留。

`AudioCaptureLifecycleSession(lifecycle, Source, Driver, Cancellation)`直接实现现有`AppMediaController.Session`和`AutoCloseable`，提供`start()/stop()/snapshot()/close()`，并提供`observe(Evidence)`、`tick()`及`requireContinuation()`。`Source.cached()`只能返回已有不可变证据，不能阻塞或启动dumpsys。`Driver.start(Cancellation)`只启动本次输入；`Driver.stopAndRelease()`须返回真实停止、释放及工作线程结束证明，不能用命令退出成功代替。

适配器使用一个延迟启动的串行工作线程`d31-audio-lifecycle`执行原生动作，控制调用只改变状态、设置取消及排队清理，不等待原生启动。没有第二个周期采样线程、没有强杀原生调用、没有自行启动网络。清理完成后关闭执行器；原生调用如果不返回，仍保留未确认状态，不能谎报线程已经退出。

## 判断与停止合同

1. 开始前只接受`NO_ACTIVE_INPUT`加其它因素`IDLE`。即便已有轨道匹配当前PID/session也拒绝接管。考虑到`AudioRecord`构造本身可能打开未active输入，允许仍新鲜的构造前空闲证据；这不消除构造至启动的竞争窗口。
2. `STARTING`原生启动完成后进入`VERIFYING`，不会直接允许输出。启动及等待首份自身证明分别最多1500毫秒；时间由每次状态读取或既有心跳检查，不能当作原生调用可强制中断的保证。
3. 自身证明复用`AudioInputOwnership.evaluate`，要求完整两源结构一致、恰好一条active轨道与固定PID/session匹配。通过后复用`AudioInputOwnershipRecords.policy`取得已交叉验证的IO，首次绑定后不能改绑。输入证据的采集起点不得早于本次原生启动完成。
4. 每源和三源组合窗口沿用1500毫秒上限，证据年龄最多4000毫秒；当前时钟回退、未来时间、过期、时间重排、其它占用、身份/请求/会话变化、IO变化及跨源不一致均撤销可继续状态。重复缓存不会更新原始证据年龄。
5. 取消、超时、异常及停止后不能通过晚到`started()`或好证据复活。错误请求号不会取消当前请求。`STOPPING`超过1500毫秒进入`RELEASE_UNCONFIRMED`，不会自动变为关闭。
6. 只有原生启动已返回、身份一致、真实stop/release均返回、采音工作线程结束、回读`recordState=0`及`recordingState=1`，且证明时间在停止请求之后且不超当前时间，才能进入`CLOSED`。迟到的真实释放证明可以关闭，超时或异常本身不能证明释放。

上述窗口不是原子快照，也不保证样本结束之后不会出现其它录音者。4000毫秒沿用归属解析器的保守有效期上限，不是已在真机证实适用于持续媒体的轮询周期。未知厂商路由、快速输入、非MIC/16k/mono形状仍按旧解析器拒绝，不能以当前有限格式覆盖宣称所有音频占用均可归属。

## 对现有Controller的具体后续接线

本节仅为后续最小修改建议，本批未改下列现有文件。

| 现有位置 | 后续必要接线 |
| --- | --- |
| `AppMediaController.Backend.create(hash, offer, cancel)`，由`execute()`调用 | 在工作路径先取得真实空闲和其它因素证据，再构造本次`AudioRecord`并实读session，固定身份后返回新的`AudioCaptureLifecycleSession`。工厂中途失败仍须清理已分配的本次资源。不得用offer自报身份或固定session代替。 |
| `AppMediaController`现有`Session.start/stop/snapshot` | 直接使用本批适配器。现有`cancelRequest`、`ownerDied`、`serviceDestroyed`和显式stop均已经调用`Session.stop`，无需另造任务。`active()`只有看到`state=closed`才释放槽位，与本批未确认释放状态兼容。 |
| `AppMediaService`现有心跳调用`controller.tick()` | `AppMediaController.tick()`目前只处理持有者租期，后续必须再转发本批Session的`tick()`或等价状态观察，才能及时取消过期采集。不能只依赖租期或用户query来推进生命周期超时。 |
| 可信归属采集工作路径 | 有界生成新鲜两源转储和其它因素缓存，推入`session.observe(evidence)`；不能在音频读取循环或每100毫秒启动dumpsys。读失败必须传播UNKNOWN，不能沿用成功状态并重写时间。真实刷新开销及竞争窗口仍需独立证明。 |
| 本次原生采音工作线程 | 原生输入启动后仍等待`VERIFYING`通过。在实际对外传递任何声音前调用`requireContinuation()`，停止后不再发布；此方法只读缓存与当前时间。当前新增Driver不负责声音传输，不应拿它替换现有传输实现而漏掉其清理。 |
| 现有运行态验收宿主 | 后续若接线，应将`d31-audio-lifecycle`纳入本次线程退出观察，检查取消后真实stop/release/工作线程结束。源码中一个daemon线程不等于实际无残留。 |

原生启动阻塞时，清理顺序保持在启动之后，避免并发release与start争用同一资源；取消标记应由驱动在实际调用前及可取消等待中检查。要达到完整业务验收，真实驱动仍须证明启动、读取及清理有界；本批不会用强杀线程或提前`closed`掩盖卡住。现有控制器兼容测试使用实际Controller源码和可控驱动，不意味着实际后端已经返回本批Session。
