# 2026-09-11 D31第三批Windows集成

## 本批范围与实现

本批将基础探针接入实际Windows候选EXE的构建、运行资源、自检和MainForm导出，不再仅交付独立命令行准备工具。沿用现有WinForms设计、图标、控件位置和.NET Framework C#编译器；没有修改Android、Web、下载URL或正式发行文件，没有执行设备操作或Git提交。

新增`research/d31_flash_tool/build-v1.6.7.ps1`作为直接构建入口，必须显式传入`CandidateId`、`BasicApk`、`FullApk`及`MetadataPath`。候选号形如`rc3`，工具版本为`1.6.7-rc3`。构建对象目录和输出目录均包含完整候选版本，任何已存在目录都拒绝覆盖；构建仅输出本地`dist-v版本`，不复制到原发布目录。

构建先复用双制品合同校验和`Prepare-BasicProbeResources.ps1`验证两份真实候选、准备基础资源，然后将唯一基础资源加入`runtimeSources`，生成匹配的嵌入资源名和`BuildConstants.RuntimeFiles`。文件名、基础资源标识和摘要都来自metadata；完整APK只作配套候选校验，不内置进EXE。新入口和当前src已去除旧`1.11.6`硬编码。历史构建脚本以及共享入口`build.ps1`保留，最终入口切换由主任务负责。

`RuntimeAssets.BasicProbe()`要求唯一、有效的基础资源描述符。`ValidateBasicProbe()`按编译进EXE的摘要验证解包文件。`ExportBasicProbe()`直接读取EXE内置字节，在目标目录生成临时文件并验证摘要后提交；缓存损坏不影响所导出的原件。目标已是相同APK时不重写，目标内容不同时拒绝覆盖；不会因目录里残留其他旧APK而选错导出源。

`Program.ValidateToolRoot()`删除旧APK文件名要求，改为检查当前基础资源的真实摘要；构建自检和界面初始化都执行这一检查。新增`--export-basic-probe <目标APK路径> <结果文件路径>`，与界面使用同一导出实现；启动失败在命令行模式返回失败，不弹出阻塞构建的对话框。

MainForm保留“首次引导/急救APK”按钮和原位置，点击后使用系统保存对话框导出当前基础APK，默认文件名来自内置资源；不再只是打开可能混有旧文件的缓存目录。`ExportBasicProbeTo()`为按钮实际调用路径，已通过加载真实EXE的测试验证。

## 修复维护标记准入

根据本轮追加合同，新增`src/MaintenanceGuard.cs`，对固定路径`/data/local/d31-remote/runtime/maintenance/repair.json`只判断存在性，不读取内容、不改写、不清理标记。设备端从可读的祖先目录逐级确认路径，要求root和目录读取成功；仅明确不存在才返回`D31_MAINTENANCE_ABSENT_V1`并放行。标记存在，无论空文件、坏JSON还是目录，都返回`D31_MAINTENANCE_PRESENT_V1`并拒绝。祖先路径不是目录、符号链接、读取失败、权限不符或回执不明确均关闭门。旧APK尚无`d31-remote/runtime/maintenance`目录时，逐级确认不存在属于正常可放行条件。

`DeviceDetector.AssertNoMaintenance()`仅对当前完整序列号和5042服务器执行一次只读ADB命令，不重置服务器、不加重试或等待、不复用旧快照。MainForm在启动“只读检查”前以及实际启动刷写后端前分别调用；备份完成后自动继续刷机同样经过后者。失败会清除旧预检通过状态和清空数据勾选，并阻止继续。

这只是Windows前置门，不能消除较长上传期间出现新修复任务的竞争。已向主任务明确交接必须修改的路径`research/d31/factory_package/flash_d31_recovery.ps1`：root核验后、设备预检返回前检查一次；ZIP上传和摘要校验完成后、写入`/cache/recovery/command`前再次检查。该最后门及跨步骤互斥由主任务统一实现；本批不新增通用修复UI，不把前置检查称为完整并发互斥。
