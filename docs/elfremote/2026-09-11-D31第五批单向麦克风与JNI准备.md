## 精确公共接线

类包名均为`net.elfradio.d31bootstrap.media`。

1. 从主任务已验证的活动核心元数据取得APK文件及小写SHA-256。`ApkMediaLibrary`只校验摘要，不重新实现包名/原签名/完整制品合同；宿主必须先完成这些核验，不能从不可信请求直接指定任意APK。
2. 只读准备使用`ApkMediaLibrary.inspect(File apk, String sha256, String abi)`，读取APK及ZIP目录，不创建缓存，不加载JNI；返回`ARCHIVE_ENTRY_OBSERVED`及`jni_loaded=NOT_CHECKED`，不表示链接器通过。
3. 单独JNI验收使用`new ApkMediaLibrary(File verifiedCoreApk, String sha256, File freshPrivateCache).load("jingle_peerconnection_so")`。构造/加载会在指定全新缓存内创建目录、解压原生库，检查大小和CRC后`System.load`；不建立WebRTC会话、不创建AudioRecord、不联网。返回false不能描述为已加载。
4. 正式平台适配器构造为`AndroidRtcMicrophone(Context mediaContext, File verifiedCoreApk, String coreSha256, File privateNativeCache, MediaCapture.Clock clock)`；设备时钟使用`AndroidMediaDevice.CLOCK`。另有`loadNativeForValidation()`供同样的单独加载验收，尚不触及音频。
5. `RtcOffer.parse(JSONObject offer, URI trustedHttpsOrigin, long nowMs)`只接受`microphone`，严格核对主机、端口、路径、唯一会话参数及45秒有效期。来源必须是现有已鉴权报告响应；令牌不进入状态结果或日志。
6. `MicrophoneSession(File privateMediaRoot, RtcOffer offer, Transport transport, Peer peer, AudioGuard guard, Clock clock, Changed listener)`配合`new MediaWebSocket()`及上述实际Peer；`start()`异步建立会话，直到真实`hello`才初始化音频。宿主对新会话创建一次对象，保留引用，断开/取消时`close()`，后台等待`awaitClosed(timeoutMs)`确认清理结果；不能在短命exec中启动后退出。
7. `snapshot()`含会话编号、状态、发布/ICE证据、会话起止及AudioRecord回调起止时间。会话时间与音频回调时间分字段；`local_recording=false`、`remote_audio_content=NOT_VERIFIED`。没有本地录音文件、没有伪造`report_id`，不能把ICE连通当成网页收到有效声音或历史录制成功。

同一私有媒体根目录的文件锁与第四批照片、录音及告警互斥；正常关闭后释放。SDP等待10秒、RPC等待20秒、ICE收集7秒，循环检查取消；独立watchdog每100毫秒检查电话/SIP否决及会话期限。网络连接及TLS握手各设置10秒期限，但系统DNS/原生调用挂起不能由Java硬性中断；关闭排在当前工作之后，未确认JNI释放时保留媒体锁并报告`release_unconfirmed`，不立即抢占新会话。实际硬件挂起、释放时延及休眠行为未验证。

## API23身份与占用门

主任务本轮反馈：独立root身份访问定位服务被拒绝，而已安装完整APP拥有其应用身份及权限。这证明不能把安装包权限直接视为root调度进程权限效果；本批不推断AudioRecord已经可用。

实际WebRTC音频字节码在API23使用`AudioRecord.Builder`，该构建路径不接收传入的Context；因此仅传应用Context不能证明底层录音归属已正确。`AndroidRtcMicrophone.open`先要求当前为本包普通应用身份且Context包名、UID对应包一致，明确拒绝root、system、shell及不匹配包，再检查`RECORD_AUDIO`。后续实际采集应由真实APP服务承载，core保留调度；服务、IPC及启动/重连由主任务后续安排，本批不新增。

`MediaReadiness.snapshot(Context, String expectedApplicationPackage, AudioGuard combinedGuard)`完全只读，分别报告权限、应用身份匹配、框架`currentOpPackageName`匹配及只读AppOps结果。隐藏框架方法不可读时明确`READ_FAILED`，不伪造归属；不公开实际UID、包清单或路径。固定`state=NOT_READY`、`audio_record_identity=NOT_VERIFIED`、`managed_media=false`、`managed_alarm_tasks=false`。只读证据不是实际录音启动及音频内容验收。

音频占用仍复用`AndroidCallGuard(Context, AudioGuard sipAndOtherOwners)`。API23可读电话`CALL_STATE_IDLE`及`AudioManager.MODE_NORMAL`作为必要条件，但公开的`getActiveRecordingConfigurations`从API24才有，不能用它证明D31全局麦克风空闲，也不能通过试开录音器充当只读检查。

`research/d31_phone_sms/source/presentation/src/main/java/com/moez/QKSMS/feature/phone/SipEngine.java`的`remoteStatus()`只提供注册状态，呼入拒接实现不能替代全局音频占用证据；`SipRemoteProvider.status()`没有活动通话快照。Nexui同样尚无本批已确认的通话状态源。需要受保护的实际电话引擎初始快照与通话生命周期证据，覆盖响铃、呼出、连接、保持、结束及源进程消失；未知、过期或读失败均否决。没有可靠源时禁止注入固定空闲guard。

## 告警长驻owner

新增`AlarmCoreOwner(Context context, File privateMediaRoot, AudioGuard combinedGuard, AlarmTasks.Changed changed)`，真正创建宿主HandlerThread并持有既有`AlarmTasks`，构造时不播放。`submit(JSONObject task, Reply callback)`异步受理，回调`completed(JSONObject result)`返回`result.alarm`规范状态；失败走`failed(String code)`。播放命令受理后主任务即可终态，声音继续由owner维持10秒，不同任务编号的停止命令可继续进入。

`reportSnapshot()`用于周期报告，`close()`安排释放并退出线程。回调应快速返回，网络上报交给主任务既有队列。接口已编译，底层第四批告警测试继续通过，但没有可靠SIP占用源，因此仍不启用`managed_alarm_tasks`，没有做真实发声或电话回归。

## 2026-09-11 108候选JNI验收的进程位宽限定

主任务已部署108。首次独立检查的私有证据为`research/d31/captures/2026-09-11/parallel-batch5-native-read108/07-stdout-private.txt`：APK摘要与v7a条目核对通过，`loaded=false`，未创建AudioRecord、未发起网络。公开记录不复制其中的临时缓存标识或其它私有字段。

主任务随后只读确认：D31的`/system/bin/app_process`指向`app_process64`，同时存在`app_process32`，系统ABI列表为`arm64-v8a,armeabi-v7a,armeabi`。108完整APK按批准构建仅含v7a；默认独立核心进程是64位，不能据设备支持v7a就推断该核心也是32位。

源码解释与上述观察一致：`ApkMediaLibrary.inspect(..., "armeabi-v7a")`只检查显式指定的归档条目，不证明当前进程位宽；`load()`依据`Process.is64Bit()`选取库，64位进程会寻找不存在的arm64条目并返回false。因此该次结果不能归因为v7a库的ART上下文、`JNI_OnLoad`或音频权限失败，也不是v7a动态链接已经失败的证据。

后续单独JNI helper必须由主任务显式使用`/system/bin/app_process32`启动，继续沿用已验证APK、小写摘要和全新临时缓存，只检查库加载，不创建AudioRecord或联网。此次限定匹配未来v7a APP媒体进程的预期位宽；APP实际`primaryCpuAbi`及运行位宽仍须由主任务按真实安装状态核对，不能只凭APK内容声称已验证。

本次仅追加文档，不改变现有64位核心架构，不增加arm64依赖或库，不修改生产加载器。32位helper的JNI成功与否等待主任务独立验收；即使通过，也不代替APP身份、电话/SIP占用和真实录音/Web验收。
