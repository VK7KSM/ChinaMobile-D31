# D31第十三批拍照与响铃业务接入

## 2026-09-12 实施范围和当前结论

本批只修改 `research/d31_adb_bootstrap` 下独立照片、响铃模块和相关测试，以及单摄像头兼容代码。未操作任何设备，未运行共享 Gradle，未修改共享 Web、`RemoteDaemon`、`RemoteProtocol`、Manifest、遥测或 `AppMedia*`。主线负责接线、统一构建、安装和生产验收。

当前结论为源码接入完成、独立编译及16项离线测试通过；不等同于真机拍摄、上传、响铃或网页验收通过。用户已明确今晚禁止任何真机响铃、警报及其他声响，必须保持该限制。

## 已核对的生产合同

- `research/FreePBX_VPNnode_Web/media-relay.js` 的 `offer` 返回 `media_session`，含 `session_id`、`token`、`mode`、`camera`、`expires_at`、`url`。`photo` 和 `alarm` 不使用 RTC，也不是 `managed_task`。
- 控制连接为既有 `/api/elfremote/media/device?session_id=...`，使用会话 Bearer。收到双方接入后的 `hello` 才开始操作；`closed`、`stop`、连接错误均结束本地资源占用。
- 复核 D22 的 `MediaSession.java`、`ReportPhotos.java`，照片使用原会话号作为 `report_id`。服务端创建会话时已生成对应手动拍照许可，无须伪造周期报告或新建编号。
- 照片上传使用 `/api/elfremote/report-photo?device_id=...&report_id=...&captured_at=...`，请求体为原始 JPEG，使用设备 Bearer。生产 `report-photo.js` 上限为256 KiB；本实现上传前检查长度和摘要。
- 只有收到 HTTP 200 且 `ok` 为布尔真、`bytes` 和 `sha256` 完全匹配，才落盘上传回执并发送 `result`。不把采集完成、连接成功或未知响应当作照片已保存。
- `media-recordings.js` 管理录音、录像分段，不适用于照片；本批没有另造录制接口或等待整套 RTC。
- 同一报告号不可替换照片。本实现不因 `switch` 重拍覆盖原件，返回结束当前会话后重新拍摄的状态；D31当前为单摄像头。多摄像头选择仍严格匹配。

## 主线固定接口

```java
new RemoteVisualMedia(Context context, File privateRoot, String apkPath, Runnable changed);
void accept(JSONObject offer, JSONObject credentials);
void tick();
boolean active();
JSONObject snapshot();
void close();
```

构造器只排队执行一次异步准备；APK摘要、Binder握手、相机数量与权限检查均在工作线程完成。`accept`、`tick`、`close` 不等待相机、网络或Binder。`snapshot` 只复制缓存。

`snapshot.managed_media_modes` 初始为空数组，准备成功后可包含 `photo`、`alarm`；`media_cameras` 保留准备时的实际数量，不因后续会话查询丢失。能力表示实现和前置条件可用，不表示实拍或实响已验收。主线负责与麦克风会话互斥及正式能力开放范围。

每两秒查询仅用于拥有者续租和状态回收，相同缓存内容不调用 `changed`，不制造每两秒一次的云上报。会话开始意图先进入本进程去重集合，未知启动结果只查询原会话，不再重发启动；照片和警报各有原编号日记，旧编号不重复拍摄或播放。

## 应用身份、服务和权限

新增服务全名：`net.elfradio.d31bootstrap.media.PhotoAlarmService`。

主线已选用独立进程 `:visual`，必须保持 `exported=false`、按需启动、`START_NOT_STICKY`。不在开机时采集或启动常驻相机。需要 `CAMERA`、`INTERNET`、`READ_PHONE_STATE`；既有受控音频占用查询所需的权限继续由主线核对，不放宽成未知即空闲。

AMS 的 Intent 只传临时握手编号、原启动标识、单调时钟和回调。实际命令、设备身份和凭据经检查调用 UID 为0的Binder发送；回调校验真实APP UID、原握手及时间窗。凭据不写入日志、文档、Intent或文件。

WebSocket 和照片 HTTPS 均调用主线公开的 `RemoteTls.factory()`，复用Android 6补充根证书。WebSocket在发送Bearer前独立校验证书链及域名，不关闭TLS验证，也不跟随上传重定向。

## 拍照行为和资源边界

复用 `MediaCapture`、`AndroidMediaDevice`、`PhotoReport`。照片使用单独相机目录和互斥锁，不检查音频空闲，也不创建录音器、请求音频焦点或修改音量、路由。真实相机占用仍由相机接口及释放状态约束。

主线只读证据指出这台D31只有一个摄像头，系统朝向为 `BACK`、角度为0。`AndroidMediaDevice.selectCamera` 仅在总数为1且请求朝向不存在时回退到camera0；总数大于1时不随意回退。采集记录的 `source` 及网页结果使用实际朝向，不把后置摄像头记成前置。

静音拍摄采用硬门：`CameraInfo.canDisableShutterSound` 必须为真，且 `Camera.enableShutterSound(false)` 必须返回真，之后才允许预览和拍摄；任一不成立即返回 `MEDIA_SILENT_SHUTTER_UNAVAILABLE`。不通过修改系统全局音量绕过。尚未取得这台设备的静音能力实测，因此不能仅凭代码宣布今晚真机拍照必定无声；主线须按用户无声限制决定是否允许实际拍摄。

照片有界采集和上传均在会话工作线程。停止时立即标记取消，socket和HTTP取消各由独立释放线程执行，不阻塞APP主线程或核心线程。真实设备释放和网络退出都完成才报告 `cleanup_complete=true`；相机释放未确认不得伪装已清理。已拍原件及匹配回执保存在APP私有目录，不记录内容到公共文档。

上传失败或回执未知不会换号重拍，也没有无限后台上传重试。本地沿用既有采集日记容量上限，达到上限明确拒绝；后续需在有真实使用证据后统一制定已确认原件的保留、归档与清理策略，不能偷偷覆盖旧原件。

## 响铃、停止和超时

复用 `AlarmTasks` 和 `AndroidAlarm`，使用本机10秒硬上限，不提升原音量。当前警报流静音则明确失败。开始前读取蜂窝、Nexui SIP和全局音频占用，未知时拒绝。播放期间只在确实持有自身Tone时豁免本地 `STREAM_ALARM` 活跃位，其他流、远程活跃、录音源、音频模式、焦点及通话状态均保持原判定。

API23的既有查询只有流级信息，不能区分本机两个同时使用警报流的播放者；这是一项明确边界，不宣称已经取得每个播放器的独立归属。主线的媒体互斥及10秒上限继续保留。

网页停止、socket断开、核心Binder死亡、15秒拥有者租约到期及10秒本机截止均触发清理。停止路径不会排在正在上传的照片后面；响铃不会因为同号重投而重复播放。服务退出前保留清理状态，未清理完成不开放后续会话。

## 2026-09-12 23:22 为138修复回执分类与终态丢失

组合构建冻结后的只读审查确认两处源码缺陷：正常会话快照包含空字符串 `error`，旧Bridge却按字段存在判定失败；服务每250毫秒清除已释放会话，而核心每两秒才查询一次，可能错过完整终态。用户明确要求修复到138，以下变更现已完成并重新冻结Java，版本号及组合制品由主线统一维护。

- 命令错误封套新增明确布尔 `command_error=true`。Bridge通过 `PhotoAlarmContract.reply` 区分命令拒绝和业务快照；业务快照即使含非空错误也完整返回，保留具体原因、原会话号和清理状态。兼容旧式没有 `state` 的纯错误封套。
- 新增 `PhotoAlarmJournal`。启动网络会话前先写不含凭据的 `visual-sessions/<原会话号>/intent.json`；资源真实释放后，将完整终态写入同目录 `completion.json`。成功拍照的原关联回执也包含在终态的 `result` 中。
- 服务只能在完成原件落盘成功后清除内存会话。写盘在控制工作线程进行；未写完不能因定时清理变成空闲。服务关闭、重建后，查询和停止仍按原会话号回读已保存终态。
- 同号启动优先返回已保存终态，不重新建立socket、拍照或响铃；只有启动意图而没有完成原件时返回明确的结果未知、`replayed=false`、`cleanup_complete=false`，不伪造成功或再次执行。
- 完成原件只写一次，不删除、不覆盖。之后的停止或失败不能替换先前保存的完成结果。目录损坏、启动意图残缺和路径越界均拒绝重放。
