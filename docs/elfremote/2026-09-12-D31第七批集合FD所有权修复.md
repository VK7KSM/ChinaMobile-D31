# D31第七批集合FD所有权修复

## 2026-09-12 现场与根因

主任务保留的完整114现场位于 `research/d31/captures/2026-09-12/parallel-batch7-cloud-missing114/fds-private.txt`。本任务只读核对，没有连接设备、重启或接替核心。软限制1024，硬限制4096，现场共有1021条FD链接：ANR源120、tombstone源120、DropBox源722、boot_id 13、pipe 2、socket 3、其它41。本文不列出源文件名、boot_id或其它身份内容。

观察：大多数泄漏引用指向扫描读取的普通源文件，而不是目录或进程管道。同一tombstone和部分DropBox源重复约12次，boot_id出现13次，与周期扫描逐轮累积吻合。主任务报告核心出现 `SocketException`，Web因报告过期隐藏未配对设备，不是身份被删除；本任务没有修改身份存储或Web行为。

源码根因为 `AndroidCollectionAccess.openRegular()` 使用 `Os.open()`取得叶FD，随后包装 `new FileInputStream(fd)`，Handle关闭仅调用 `stream.close()`。API23此构造借用传入FD，不承担其所有权，因此try-with-resources调用成功也没有关闭原始FD。主任务另行确认了API23关闭语义。`AndroidFaultSources.signature/readProc` 已使用try-with-resources，调用者的正常关闭并未缺失，缺陷在底层Handle。

`FaultDirectoryWalker` 的普通路径使用ParcelFileDescriptor固定目录，并关闭原始目录FD、固定副本和子进程流；本次现场不支持将普通源文件逐轮重复归因于目录walker。因此未修改walker、来源选择、扫描预算、候选签名或原件容量合同。

同目录审查还发现 `AndroidEvidenceStore.storeNew()` 使用 `new FileOutputStream(fd)`，同样没有承担 `createArtifact()`原始FD的关闭。该输出路径一并修复，不能只处理扫描输入。

## 最小修正与关闭边界

- `AndroidCollectionAccess`：`OwnedHandle`显式拥有FD，以 `Os.read/fstat/close`执行操作；系统读取返回0的EOF转换为原Handle约定的-1，零长度请求仍返回0。读取、stat和关闭串行；关闭仅尝试一次，关闭后读/stat拒绝，避免旧Handle操作已复用的FD。关闭失败传播，不能依赖GC或重试关闭整数FD。
- `AndroidEvidenceStore`：以 `Os.write`循环处理短写，每次至多65536字节，写完 `Os.fsync`；单一Closeable拥有者在正常、写入异常、同步异常和非受检异常中关闭原FD。失败继续报告 `STORE_WRITE_FAILED`，留下已创建的证据文件，不清除、不覆盖、不伪造成功回执。
- 叶文件打开与排他创建在父目录关闭成功后才移交FD，避免父目录关闭异常时失去叶FD所有权。
- 集合目录固定副本创建统一为 `pinAndCloseOriginal`：dup失败仍关闭原FD；原FD关闭失败则同时关闭已创建副本。保留原有 `O_NOFOLLOW/O_NONBLOCK/O_EXCL`、权限、祖先固定及真实stat身份检查。

本任务未修改主任务独占的 `FileOperations.java`。其旧114同进程64轮 `before=15/after=207/delta=192`、每轮3个FD泄漏由主任务独立确认，证据位于 `research/d31/captures/2026-09-12/b7-fd-file114/`；不能把本任务的集合helper结果替代该文件操作对照。
