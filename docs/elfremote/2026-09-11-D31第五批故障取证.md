## 固定命令合同

通过已有`root_exec`执行公开类`net.elfradio.d31bootstrap.faults.FaultCommand`，APK路径使用已经核验的实际活动版本，不写死106或本批候选编号。

```text
index <1至64>
index <1至64> <nextAfter>
query <eventId>
export <eventId>
archive <eventId> <zip_sha256> <zip_bytes> <manifest_sha256>
```

`eventId`及摘要均为64位小写十六进制。`index`保留旧单参数用法，返回`hasMore`和`nextAfter`；需要下一页时通过`FaultCommand`传回游标。旧`FaultQueryCommand`仍保留原查询用法，没有改成新的Web任务类型。

新增公开Java入口：

```java
new FaultExports(File root, FaultSources sources, FaultPolicy policy);
JSONObject exportEvent(String eventId);
JSONObject archiveEvent(String eventId, String packageSha256,
                        long packageBytes, String manifestSha256);
FaultMonitor.readIndex(File root, int limit, String afterEventId);
```

方法按原有约定抛出异常；生产仍使用`AndroidFaultSources.ARCHIVE_ROOT`、`new AndroidFaultSources()`及`FaultPolicy.defaults()`。没有新增第三方依赖，ZIP使用API23已有的Java标准库。

导出回执字段固定如下，`path`直接供已有`get_file`使用：

```json
{
  "schemaVersion": 1,
  "kind": "FAULT_EVENT_EXPORT",
  "eventId": "<事件摘要>",
  "exportNumber": 1,
  "state": "EXPORTED",
  "path": "/data/local/d31-remote/faults/<事件摘要>/exports/export-1/bundle.zip",
  "bytes": 12345,
  "sha256": "<整个ZIP摘要>",
  "manifestSha256": "<清单原始字节摘要>",
  "manifestBytes": 1234,
  "files": 5,
  "evidenceBytes": 10000,
  "captureState": "COMPLETE",
  "completeRawFiles": 1,
  "scope": "ALL_FROZEN_EVENT_FILES",
  "sourceCompleteness": "SEE_MANIFEST_GAPS",
  "downloadState": "NOT_ACKNOWLEDGED",
  "rawContentInSummary": false
}
```

以上数字和摘要占位仅说明字段，不能用作验收数据。`EXPORTED`只表示本机导出并回读校验通过，不表示服务器接收或电脑已经保存。重试导出会核验并重用同一已提交包及回执，不覆盖旧制品。

## 清单与完整源判定

ZIP根目录包含`manifest.json`，其原始字节摘要必须等于回执`manifestSha256`。其余每个ZIP条目名称均为`evidence/`加清单的相对`path`，没有解包所需的绝对路径。

`manifest.files[]`固定字段：

```json
{
  "path": "attempt-1/fault-source.bin",
  "bytes": 123,
  "sha256": "<小写64位摘要>",
  "role": "RAW"
}
```

二进制原件的角色为`RAW`，JSON等记录为`METADATA`。清单还包含`schemaVersion`、`kind=FAULT_EVENT_BUNDLE`、`eventId`、`category`、`phase`、`files`、`totalBytes`、`rawFiles`、`gaps`、`rawEvidence`及明确未判定的根因和系统一致性。

`rawEvidence`同时出现在事件查询、索引及包内清单中：

```json
{
  "captureState": "COMPLETE",
  "completeRawFiles": 1,
  "partialRawFiles": 0,
  "items": [
    {
      "artifact": "attempt-1/fault-source.bin",
      "completeOriginal": true,
      "bytes": 123,
      "sha256": "<原件摘要>",
      "state": "COMPLETE"
    }
  ],
  "completenessBasis": "DIAGNOSTIC_COMPLETE_AND_SOURCE_SIZE_AND_STORED_SHA256"
}
```

`completeOriginal=true`要求三项同时成立：原诊断项`state=COMPLETE`；原诊断`before.size`等于实际保存的原件长度；实际原件长度、SHA-256与原诊断保存回执一致。不存在、摘要不符、缺少原长度、原诊断截断或部分读取均不能算完整。

主任务选真实验收事件应分页查找`category=ANR`或`TOMBSTONE`、`rawEvidence.captureState=COMPLETE`、`completeRawFiles>0`，并至少有一项`completeOriginal=true`且`bytes>0`。总体`phase=PARTIAL`可能仅表示事前或事后窗口缺失，不能把它等同原件读取失败；反过来也不能把`captureState=PARTIAL`当成完整源。

导出包含事件目录中所有允许的已保存文件：事件描述、状态快照、已有前后窗口、所有尝试报告、成功或失败尝试留下的实际原件。它不重新读取`/data/anr`或`/data/tombstones`，不会用后来变化的现场冒充已冻结原件。原采集的256KiB上限及截断事实保持；“完整导出包”表示完整包含已保存事件文件，不表示把历史缺失或截断的源日志补齐。

缺口在`gaps[]`保留固定原因及适用相对路径，例如事前连续日志不可用、前后窗口不完整、缺少已声明原件、源文件截断、原件与诊断回执不符、尝试中断、报告不可读及没有保存原件。包可携带部分证据，不将部分证据改名为完整故障原因。

## 显式归档合同

导出仅接受终态`COMPLETE`或`PARTIAL`事件；仍在采集、重试或等待后窗口的事件返回`EVENT_NOT_TERMINAL`。打包与采集共用既有`collector.lock`，忙时立即拒绝，不等待设备全局维护锁。

第一次导出写入排他的`export-seal.json`，冻结终态事件的后续观察计数写入，防止下载期间状态文件变化使包失效。封存不会释放活跃名额；即使导出失败，事件仍保持活跃并保留全部已写证据。每个事件最多两个导出尝试，使用不同子目录；无完整回执的残留包不能归档，也不会被下一次覆盖。

电脑先经`get_file`取得回执指定ZIP，核对整包长度及摘要，再核对内置清单摘要、精确条目集合、各原件长度及摘要，之后显式调用`archive`并传回已核验的四项身份/内容参数。设备端再次验证回执、ZIP、清单及当前冻结文件集合，确认没有新增、删除或变化，才排他写入`archived.json`。

归档回执为`state=ARCHIVED`、`activeSlotReleased=true`、`originalsDeleted=false`、`releasedBytes=0`。回执还说明确认来自调用者的明确摘要确认，不伪装成设备独立证明电脑或远端永久存储已经落盘。宿主核验和任务原件必须保留，不能只凭设备生成了ZIP就调用归档。

缺少导出回执、摘要/长度不匹配、ZIP或清单损坏、原件变化均拒绝归档。已经归档的相同确认会回读原回执；包或回执后来损坏时，活跃计数核验失败，事件重新计入活跃容量，不继续宣称具备有效归档证明。

导出回执本身保持生成时的`downloadState=NOT_ACKNOWLEDGED`，不回写；当前是否已显式归档见事件`export.archived`及独立`archived.json`。这样既保留最初导出事实，也不覆盖后续确认记录。

## 容量与旧源去重

默认活跃事件上限仍为32，保留事件总数新增硬上限128。原事件目录和去重摘要一直保留；已归档旧源再次被扫描时仍命中同一目录，不新建事件、不重新采集、不重置观察记录。只有来源身份真正变化才按原发现合同成为新的候选；有限前缀和元数据检测的已知边界没有在本批扩大。

总磁盘预算仍为64MiB，包含活跃原件、已归档原件、ZIP副本、清单、回执及所有失败导出残留；默认保留32MiB可用空间。退出一个活跃名额不是释放磁盘，归档后实际占用通常还增加一个小回执。

单个事件最多48个导出文件，单文件最多1MiB，ZIP最多8MiB，两个导出尝试均计入实际使用量。ZIP采用不压缩存储，逐文件流式写入并设置硬输出上限，不引入压缩膨胀或无界内存打包。路径来自受控事件文件树，只允许固定层数及文件名规则；拒绝目录穿越、符号链接、嵌套意外目录及报告注入的跨目录原件引用，不递归打包整个故障根目录。

总空间或可用磁盘不足时，导出在预检返回`EXPORT_CAPACITY_LIMIT`；活跃/保留数量或总字节达到上限时，扫描记录`CAPACITY_LIMIT`并停止新增。没有足够空间完成导出时，不通过删原件、删除失败包或把归档当作空间释放来绕过限制。后续扩容或清理需要独立明确处理，本批不执行自动清理。

索引`scan`增加`activeEvents`、`archivedEvents`、`retainedEvents`、`retainedBytes`及相应上限。它记录采集时刻的计数；归档命令返回之后，下一轮扫描更新这些统计，事件即时查询可直接读取归档状态。

## 2026-09-11：整合审查后的校验缓存修正

总负责人指出原`isArchived()`会每60秒完整读取所有已归档ZIP，查询还会重复读取。该问题成立；本线在冻结前修正，命令及原有回执字段保持兼容。

生产缓存使用实际`Os.lstat()`身份，绑定`archived.json`、导出回执、清单和ZIP的设备号、inode、长度、修改时间、状态变更时间、权限、属主、组及链接数。首次访问、任一身份变化或缓存淘汰后才重新核验整包及清单；核验前后再次核对身份，避免把变化过程记为稳定结果。不存在归档标记与存在标记是不同缓存身份。

最多缓存128个事件的导出校验结果。查询中的原件摘要另有最多384项缓存，同样绑定实际文件身份，只保存摘要和核验元数据，不缓存原始内容。原诊断项和其长度/摘要声明仍重新读取核对；缓存只消除大原件重复读，不跳过诊断完整性条件。常驻扫描在缓存命中时不读取旧ZIP内容，查询连续访问也不重复读取相同原件。

事件`export.verification`新增`mode=FULL_HASH`或`STAT_CACHE`、`verifiedAtMs`及`scope=EXPORT_PACKAGE_AND_MANIFEST`；原件摘要项新增`verificationMode`和`verifiedAtMs`。`unchangedStatIsNotContentProof=true`明确说明stat身份未变只支持复用此前核验，不是本次重新证明全部字节未变。API23公开stat时间为秒精度；刻意同身份、同长度且时间元数据不变的改写不由缓存独立排除。

缓存仅在本进程内有效。常驻核心可跨周期复用；每次独立`app_process`查询第一次读取会全量核验，该进程中随后摘要和归档状态检查复用结果。核心重启会冷启动缓存，不把缓存持久文件当作可信证明。损坏包在首次或身份变化后的核验会失去归档名额释放资格；身份完全不变时只能维持此前核验状态，不能将其描述为持续字节监测。

显式`export`及`archive`始终绕过缓存，完整读取核对ZIP、清单和冻结原件，即使stat身份没有变化也不能仅凭缓存放行。测试专门用固定身份模拟这种情况，确认两个显式命令仍拒绝已被修改的ZIP。

新增回归覆盖缓存命中、ZIP变更、归档标记变化、回执文件替换、原件变化，以及显式导出/归档强制全量校验。最终独立Java8编译通过，59项执行、58项通过、零失败、1项Windows符号链接权限跳过，耗时11.345秒。证据为`research/d31/staging/faults-offline-20260911-223702-133/`，结果原文`{"run":59,"failed":0,"ignored":0,"assumptions":1,"passed":58,"elapsedMs":11345}`。旧55项证据不改写。

本次只修本包与对应测试，未修改公共调度或执行共享构建。源码再次冻结，设备真实IO耗时和最终生产取回/归档结果仍由主任务记录。

## 2026-09-11：108运行中的QUIK崩溃与捕获边界

本次仅只读复核源码及既有原件，未连接设备、修改源码或重跑构建。原件为`research/d31/captures/2026-09-11/parallel-batch5-runtime108/services-log-private.txt`。第2021行记录22:51:00.030的`FATAL EXCEPTION: WM.task-1`，第2023行进程为`dev.octoshrimpy.quik.fdroid`，第2025行异常为`java.lang.ClassCastException: androidx.work.impl.workers.ConstraintTrackingWorker cannot be cast to androidx.work.Worker`；第2029行调用栈进入`InjectionWorkerFactory.createWorker`。第2061行随后出现`android.intent.action.DROPBOX_ENTRY_ADDED`广播，第2073行记录`cause : data_app_crash`。

已确认这是QUIK的Java未捕获崩溃。邻近的广播与`data_app_crash`日志支持系统已处理这类故障来源，但广播未展开附加字段，本次没有取得对应DropBox文件名或elfRemote事件回执，不能宣称已精确关联到某个文件，更不能宣称该次原件已被elfRemote保存。

`AndroidFaultSources.accepts()`接受`/data/system/dropbox`下的`data_app_crash@<数字时间戳>.txt`、`.dat`、`.lost`及可选`.gz`名称，没有应用包名或异常类型白名单。因此QUIK与该`ClassCastException`本身不会被筛选器排除。事件分类为`DROPBOX`，不是`ANR`或`TOMBSTONE`；主任务应分页读取索引并在返回结果中筛选`category=DROPBOX`。当前仅挑ANR/TOMBSTONE完整原件的导出验收选择条件不能用于判定此Java崩溃是否已捕获。

实际捕获还受以下现有边界约束：

- 公共调度首次等待60秒，此后按60秒固定延迟检查；仅启动完成且无维护预留时提交采集，不依赖云注册。没有监听DropBox新增广播，也没有常驻logcat或进程退出检测。因此不是崩溃发生时立即冻结，轮询前被系统清理或替换的源可能漏采。
- 四个来源共享5秒发现预算，DropBox为第三个来源。每个目录最多枚举64个名称、32768字节输出，先枚举限额再按名称筛选，不匹配名称也占名额。后续mtime降序排序只作用于已发现候选；没有目录分页或轮转，未进入前64项的新DropBox文件可能在重复轮询中持续漏掉。不能以“下一轮一定采到”解释该限制。
- 文件必须存在、可读、为普通文件且读取时身份稳定；来源变化会拒绝。`scan.coverage.sources`中的`UNAVAILABLE`、`PARTIAL`或`NOT_CHECKED`及原因可区分权限、枚举、读取或时间预算缺口，不能把未发现等同无崩溃。
- 每轮最多推进或新建8项，默认最多32个活跃事件、128个保留事件，总预算64MiB并保留32MiB可用空间；数量、预留空间或总字节门不满足时停止新增。显式归档仅退出活跃名额，不删除原件、不释放磁盘。已归档来源的身份仍参与去重。
- 单源最多保存256KiB，超过上限保留有界前缀并标记截断；可重试的读取等失败最多尝试3次。`.gz`保留原始压缩字节并标记`GZIP_RAW`，不解压解析异常；以`.lost`结尾的源明确标记`PARTIAL / DROPBOX_ENTRY_LOST`。完整导出只证明已保存内容完整进入包，不能补回系统已丢失或此前截断的日志。

本次崩溃的捕获结论仍为“源码覆盖该来源类型，具体事件未核实”。确认需要主任务取得对应`DROPBOX`事件、导出包与原始诊断回执，在宿主核对时间和实际异常文本；压缩源应另在宿主解读，且保持下载原件不可变。完整性仍按`sourceLogComplete`及`gaps`判断，不能从异常摘要推断完整故障前后窗口或业务根因。本线不诊断或修复QUIK业务代码。
