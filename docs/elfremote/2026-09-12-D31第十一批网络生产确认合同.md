现有`Binding`包含本地任务号、APK、原boot、前像、目标、开始/截止/最近单调时间；`Receipt`只含本地任务号、APK、boot、目标、开始、截止、nonce和请求时间。前像由`requireMatch`在本地提交时检查；设备身份、云端任务号和操作键必须由生产Source及Web外层核验，不能假定Java Receipt已包含它们。

现有`query/report`没有完整输出`boot_id/started_elapsed/apk_sha256`，并固定输出`connectivity=NOT_CHECKED`；不可凭其显示字段拼凑完整确认请求。生产适配应序列化受保护的Binding，并验证云端原号映射。`restored=true`仅对应实际`ROLLED_BACK`且原像回读通过；`ORIGINAL_OBSERVED`不能擅自改写为执行过回滚。

`elfRemote/control-plane.js:410`先查同id或幂等键：摘要相同返回原任务，否则冲突；随后在`pending/claimed/running`时拒绝其他普通任务。幂等摘要仅覆盖规范化后的`type/params`，不含外层`expires_at`。同号重送并改变外层期限仍返回原期限，不能以重试延长窗口。

`system-settings.js`当前不支持Wi-Fi布尔开关键，且D31有限能力白名单明确拒绝网络写。未知参数会被规范化剥离，不能偷偷添加`network_transaction`便声称参与了幂等校验。现有`connect_wifi`指向另一套SSID连接语义，不适合冒用为本次开关事务。

`RemoteTasks.accept`还有设备侧普通任务槽：已有未生成receipt的任务时不接收下一普通任务；任务执行意图及回执持久化。网络确认不能排在该槽后面。通用命令收尾以进程正常完成和退出码0判断成功，而网络`begin`可以返回`AWAITING_CONFIRM`后退出0，**直接套用会提前成功**。须在原任务执行器增加网络子合同分支，继续保存同一个云端任务及本地id，仅以持久网络终态收尾。

## 三、建议精确流程

1. 管理员仍通过`POST /api/elfremote/task`创建一个`system_config`任务。建议采用`group=wifi/action=set/key=enabled/value=<布尔>`，增加规范化且参与原摘要的`network_transaction={version:1,apk_sha256,confirm_within_ms}`。这些键是待协调建议，当前请求会被拒绝；不可先开放按钮。
2. 设备依现有领取和进度链路持久保存原任务，确认`claimed/running`后才开始本地动作。本地网络任务号沿用`RemoteProtocol.localJobId(device_id,cloud_task_id)=SHA-256(UTF-8(device_id+":"+cloud_task_id))`，并持久保存原云端任务、期限、规范化参数和对应APK；不让Web96字符编号直接穿过网络本地64字符token门。
3. 原APK创建真实前像、维护预留和journal；独立恢复守护完成握手，才允许setter。只有明确读回目标才进入`AWAITING_CONFIRM`。`before==target`直接`UNCHANGED`，作为未改变配置的终态报告，不声称发生了管理链路验证。
4. 独立确认执行者从原预留找到原APK和任务，在同boot、未过期、状态正确时调用`pollConfirmation`。启动优先采用begin后的立即触发，并由固定监督补偿核心重启后的缺口；确认执行者是独立进程，不是主核心线程定时器。没有预留不启动，不持维护锁或journal锁等待HTTP。不能把HTTP加入恢复守护同步循环而拖延回退。
5. 建议复用`POST /api/elfremote/task-progress`，增加待协调子动作`action=network-confirmation`，外层仍为原`device_id/token/task_id/state=running`，内层为`network_confirmation`请求。这个分支不调用普通enqueue，也不进入通用成功推进；它只能检查和记录同一个已存在原任务的确认决定，不能创建任务或重发begin。
6. Web在现有DO串行事务内验证设备token、设备未停用、原任务为正确网络子合同且running、云端期限有效、原请求摘要一致、未取消、原本地任务号计算一致、目标/窗口/APK符合已批准意图。首次有效请求把boot、开始和截止等本地绑定附属到原任务，之后不可改绑；服务端不靠回显任意客户端JSON授权。
7. Web持久记录“已发放确认允许”，返回严格语义回执，完整回显本次绑定及nonce；原任务继续running。生产Source验证HTTPS目的地、设备/云端任务、协议版本、响应字段类型、语义及绑定后才能构造Java Receipt。只有200、`ok=true`或任意报告成功时必须返回无确认或明确错误。
8. 客户端回包后及本地提交锁内再次核验，读回目标并持久写`CONFIRMED`。守护与确认通过同一journal序列化；任何阶段丢失云连接都不暂停本地恢复预算。若释放维护预留失败，即使终态已经落盘仍需原号核查释放，不重写网络。
9. 按现有`task-progress`补传原任务的结构化终态，Web核验后才写success/failed等外层终态。管理员只通过现有原号GET追踪。不能由“服务端允许已发放”提前显示成功；ACK丢失只补传或查原号，不生成第二个任务。

## 四、字段和绑定表

下表为建议线协议字段，camelCase Java成员需要明确转换为表内snake_case。所有样例值应使用合成数据，设备token及真实标识不进入公开文档或模型结果。

| 字段 | 来源、验证和幂等关系 |
| --- | --- |
| 外层`device_id/token` | 沿用当前设备凭据；Web验证token摘要归属，Source使用本机当前凭据；不创建第二套账号或签名体系 |
| 外层`task_id` | 云端原任务id；与`idempotency_key`和`request_digest`组成既有去重机制，不作为新任务id |
| `version` | 建议网络确认子合同版本1；未知版本拒绝，不退化成普通HTTP成功 |
| 内层`task_id` | 原本地网络号，为既有device+cloud任务id的SHA-256；云端id与本地id是不同字段，禁止互换 |
| `apk_sha256` | 任务意图冻结的APK，必须等于维护预留及实际运行冻结release；不能用最新版本或系统基线替代原APK |
| `key` | 固定`wifi_enabled`；当前不支持其他网络操作 |
| `before/target` | 布尔真实前像和目标；目标必须等于原`params.value`，前像首次登记后固定，并由本地提交重验 |
| `boot_id` | 原事务boot；不是Supervisor当前boot。整机重启后禁止把它更新成新boot继续确认 |
| `started_elapsed/deadline_elapsed/window_ms` | 原本机单调时间及窗口；`deadline=start+window`，生产窗口10000至120000毫秒；同号不延长、不重算 |
| `issued_elapsed` | 本次请求时间；要求不早于本地`last_elapsed`及开始时间，严格小于截止；返回必须原值一致 |
| `nonce` | 每次poll新UUID，绑定单次请求；同boot核心重启也生成新值，旧响应不能用于新poll |
| `request_digest` | 原Web规范化意图摘要，与APK摘要分开；建议在响应外层携带并由Source核对，不能用客户端任意自报值取代服务器原任务 |
| `last_elapsed` | 本地journal防时间倒退依据；随原事务核查更新，不应作为服务器不可变绑定字段，否则合法recover观察后会冲突 |
| `expires_at` | 既有云端绝对期限，只限制服务器发放/下发；不可与设备elapsed直接相减。已发请求在本地仍以原boot和deadline为硬门 |

nonce不是新的任务号，也不是新的长期密钥。普通重试复用同一在途请求时只接受同nonce同字段；新的poll生成新nonce。服务端可以重新发放同一原绑定的新nonce响应，但不得延长deadline或改变已记录绑定。使用有界附属记录或保留最近响应即可，不积累第二套无限挑战任务历史。

## 五、独立调度和维护约束

| 约束 | 建议处理 |
| --- | --- |
| 普通Web或本机任务仍running | 确认分支直接处理原任务，不需要释放该槽，不通过`RemoteTasks.accept`新建任务 |
| journal/maintenance忙 | 原绑定、前像、期限不变；有界退避后重新取快照和新nonce，期间独立回滚不被HTTP阻塞 |
| 核心退出或同boot重启 | 固定监督从原预留启动原APK确认执行者；先query状态，未过期才取新nonce；不重放begin、不续期 |
| 整机重启 | 原boot已失效，确认禁止；只走已验证的原事务恢复及新boot服务就绪门。恢复成功后必须新建由管理员发起的新操作才可再次改变网络 |
| 原APK不存在、摘要错误或缺确认实现 | 停止确认并保留原因，恢复使用既有路径；不拿新版替代原事务。本批132只有本地合同，不能事后声称已有生产Source |
| 无待确认事务 | 零确认联网、零额外常驻轮询；不改变普通上报间隔 |
| 请求耗时和429/503 | 全链路预算不超过`min(3000,剩余)`并可取消；遵守有界退避，退避超过剩余窗口则停止发新请求，由守护恢复 |

现有`RemoteHttp.cloud`连接15秒、读取20秒且仅检查ok，不能不加适配直接实现Source的三秒上限；DNS、连接、写出和读取都需要有界收集/关闭，不能只设read timeout。沿用认证、禁重定向和HTTPS策略，但明确增加预算入口及严格回执解析。恢复守护150秒是停止新增恢复操作的预算，不是生产确认的延长期限，也不承诺Binder硬取消或绝对退出时刻。

现有Supervisor十秒恢复退避保持；新确认不能只依赖它来保证十秒窗口内响应。建议正式默认窗口60000毫秒、立即启动确认子进程并在原期限内有限重试，准确延迟与性能需主线实测。错过短窗口时应真实回滚，不为了“成功率”改原截止时间。

## 六、丢失、重启和重复确认

| 场景 | 必须的结果 |
| --- | --- |
| 请求未到服务器、鉴权失败或CF不可用 | 不确认；不延长本地期限；按原事务恢复 |
| 服务器发放后响应丢失 | Web显示允许已发放、设备提交未知；同原绑定新nonce可再次验证，不能显示网络已成功 |
| 旧响应在新poll或核心重启后到达 | nonce不同拒绝；从当前状态取新请求，不能复用落盘旧响应直接提交 |
| 响应到达时截止恰相等 | 拒绝，采用严格`now<deadline` |
| 回包期间boot变化或elapsed倒退 | 拒绝；整机重启走恢复，不把新boot当原窗口的续期 |
| 守护先回滚，响应随后到达 | 不得复活任务或重新setter；查回滚终态，Web不得据旧允许覆盖它 |
| 已CONFIRMED但最终上报丢失 | 同号补传持久终态；不得重跑网络写入；独立确认再次poll不等于重做成功 |
| 已终态且预留已释放，再poll | `awaiting`先检查原预留，可能明确报预留不存在，而非必返回`NOT_WAITING`；应查原journal终态和原任务回执，不把这个错误当网络失败重放 |
| 日志UNKNOWN或NEEDS_ATTENTION | 保留预留、前像与错误，显示需核查；不得伪装ABSENT、新建同目标替代任务或普通success |
| 服务器重启/DO重建 | 从同一原任务附属状态恢复，不能丢失绑定后对旧id重新授予不同boot或期限 |
| 浏览器刷新、退出或无管理员在线 | 设备凭据确认仍可完成原已授权操作；浏览器只读查原号，不需保持页面轮询，不增加二次人工确认 |

取消竞态需要明确线性化点：建议服务器尚未发放允许时，原号cancel优先阻止发放；一旦允许已持久发放，取消不能宣称撤销已在途的回执。该阶段回“允许已发放，等待原号最终核查”，不得沿用通用cancel假承诺一定回滚。原因是设备`cancel`对已CONFIRMED终态不会再反向写网络，跨进程/跨网不能靠晚到取消保证撤销。若要在确认后撤销，需读取当前状态并另行明确发起新操作；本批不自动生成新任务。

另一重要边界：只读到Wi-Fi开关目标，加上变更之后经已有管理服务严格授权的往返，可以证明“该开关目标下管理链路仍可达”。在以太网仍连接时，这不证明Wi-Fi已关联、SSID可用、SIM数据可用或流量确实走Wi-Fi。本批不得把保留有线的验收写成Wi-Fi链路切换通过。不要为追求这个更强结论引入未经实现的网络目标种类。

## 七、状态与成功语义

继续使用一个原Web任务：`pending -> claimed -> running -> success/failed/rejected/expired`。本地细阶段放在原任务的结构化网络子结果中，不增加通用任务队列状态。

- `AWAITING_CONFIRM`、服务器允许已发放、清理未完成：外层仍running，明确当前阶段。
- `CONFIRMED`且绑定完整、目标回读及本地持久提交证据有效：才可success；最好等待原预留释放核查完成再收尾。
- `UNCHANGED`且未调用setter：可标success但显示“目标原已如此、未修改”，不能显示已验证管理链路。
- `ROLLED_BACK/ORIGINAL_OBSERVED/ABORTED`：目标操作未完成，保留其准确含义及原值核查，不当网络变更success。
- `NEEDS_ATTENTION/UNKNOWN`：未解决，继续保留原任务及本地预留，网页明确需核查，不能因为上传成功而success。

当前`applySystemSettingsResult`只解析`exit_code/action/text/applied`，不理解网络事务；现有`publicRepair`也没有透传完整网络绑定结果。这两者都要加网络子合同分支。现行任务过期逻辑会置expired并清空`system_config`参数，随后又可能让其他任务入队；建议对已dispatch的网络任务保留原绑定和参数直到设备终态核对。服务器期限过了可以停止发放确认，但不能认定设备已恢复，更不能让历史结果处理忽略晚到的原任务真实终态。

历史任务通常保留30天，设备网络journal128条且不自动清理；这不是无限幂等保证。需要沿现有显式归档体系保留必要去重摘要，未归档/未知不能删除原任务依据。本批不设计另一个历史库。
