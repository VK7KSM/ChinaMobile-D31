## 核心重启与整机重启的合同

| 情况 | 调度与恢复行为 | 禁止行为 |
| --- | --- | --- |
| 仅核心进程重启 | 保留原任务、冻结APK、前像、目标、原boot及原elapsed期限。已有独立守护身份与新鲜心跳通过时复用，否则尝试重新拉起守护。等待确认尚未过期时保持原期限 | 不重放`begin`、不重置确认窗口、不把主核心内线程当独立守护 |
| 整机重启 | 新进程的心跳使用当前boot；事务绑定仍使用原boot与期限。恢复器发现换boot立即走原事务恢复，不等待旧期限 | 不接受旧确认，不用新启动的elapsed解释旧确认窗口，不把旧Binder未知状态当作跨启动仍在运行 |
| 写入前PREPARED中断 | 原值未变可报告`UNCHANGED`；外部已改变则保留`NEEDS_ATTENTION` | 不补执行原目标，不接管未执行写入后的第三方变化 |
| 已有终态但预留未释放 | Journal锁内重读终态并匹配维护预留后释放 | 不因之前一次查询为终态便在锁外删预留 |
| 维护预留已有但事务真ABSENT | 验证完整日志及原预留，Journal锁内释放尚未开始的预留 | 不把日志损坏、丢失、忙锁或权限拒绝解释为ABSENT |

开关原值回读与管理链路恢复仍不同。`ROLLED_BACK/restored=true`保留第九批严格恢复setter和真实回读合同，`ORIGINAL_OBSERVED`不能升级为已恢复；`connectivity=NOT_CHECKED`保持。

### 启动接续

```java
new NetworkAndroidPlatform(digest, access).resumeRecovery(originalTaskId);
```

其中`access`为绑定同一摘要的现有`RemoteNetworkAccess`维护桥。主线增加本地命令`resume <原任务号> <原APK摘要>`；这不是生产Web任务名。

Supervisor在每轮外层、取得maintenance锁之前读取受保护的`repair.json`。仅对`kind=network`取`network_task`与`plan_sha256`，用对应冻结APK的CLASSPATH启动独立协调子进程；不能持maintenance等待子进程，不能用当前活动APK替换原事务APK。根命令继续核验D31平台、root、完整参数与冻结APK摘要。启动调度不依赖CF或普通云任务忙槽。

`resumeRecovery`在Journal锁内核验持久原像和维护预留。需要守护时调用现有setsid启动与实际进程身份握手；握手先心跳、后取Journal锁。已有守护必须同时通过任务、APK、原boot、当前boot、原期限、实例、PID、root UID、内核starttime及真实APK/ART映射核验，不能只看进程名。

返回值保留原事务回执并增加：

| 字段值 | 含义 |
| --- | --- |
| `recovery_dispatch=GUARD_READY` | 已有或新建守护握手通过，尚不代表网络已恢复 |
| `recovery_dispatch=SETTLED_RELEASED` | 已有明确终态且匹配预留释放成功 |
| `recovery_dispatch=UNSTARTED_RELEASED` | 真ABSENT且匹配预留释放成功，没有执行网络写入 |

忙锁、存储损坏、绑定不符和握手失败抛异常且保留现场。主线须按原任务与摘要有界等待、退避，不能每轮无条件重新拉进程。即使协调进程超时，也不能杀掉已setsid独立的守护；后续先查询原号和检查心跳。

同一boot内守护已有`NEEDS_ATTENTION/UNKNOWN`结果时，新增持久结果字段`guard_task/guard_apk_sha256/guard_armed_boot/guard_boot/guard_deadline`用于严格匹配。自动接续返回`NETWORK_RECOVERY_ATTENTION_REQUIRED`，不再次拉起相同恢复动作，避免未返回Binder调用或损坏日志造成开机循环追加。主线遇此错误应停止该原号自动重拉，保留现场；可由显式原号`cancel`处理。真正换boot后可重新核验与恢复。此结果文件不包含网络凭据。

### 固定基线与旧事务兼容

128及更早的冻结APK没有本批`resume`入口。新Supervisor不得因为当前已安装新版便拿新版代码接管旧摘要事务。遇到旧APK不支持新入口，应明确报告并保留预留，可沿已有受控旧版guard命令处理；自动兼容旧事务不属于本批已验收能力。新版公共启动接线必须显式更新固定系统Supervisor后才可能在下一次启动运行。仅覆盖安装新版普通APK不等于固定监督已经升级。

### 独立确认

```java
platform.pollConfirmation(originalTaskId, verifiedSource);
```

`verifiedSource`实现`NetworkConfirmationDispatch.Source.fetchVerified(Request, maxWaitMs)`。它必须验证真实管理链路、认证来源及请求绑定；没有本批生产HTTP实现。仅普通HTTP200、普通心跳或本地测试替身都不能作为生产确认。

调度与普通任务领取分开，不能给正在等待确认的普通忙槽再排一个确认任务。一次调用先在Journal锁内取得原记录快照并验证维护预留，释放锁之后才发有界、可取消的认证请求；预算为剩余原期限与三秒的较小值。守护独立运行，因此确认请求挂起不得持有Journal锁或阻止超时恢复。确认调度自身不是独立进程守护，不能用它替代setsid回退进程；主线需独立于普通任务忙槽安排其执行。

回执严格匹配原任务号、APK摘要、原boot、目标、开始elapsed、原期限、当次随机值及请求elapsed。收到后再次检查boot和期限，再在真实事务锁内重读原绑定、核验目标并提交；联网期间被取消、过期回滚或记录被替换不能通过旧回执复活原任务。同号再次轮询使用新随机值，不重发原写入。

`Source`接口约定须有可取消的传输超时；本批只提供可注入本地合同，没有验证某个生产HTTP库遵守超时。普通任务分发、认证端点和生产字段透传需后续与Web工作线冻结，不能根据这些Java字段自行发明Web任务名。本批不开放网络写入能力。

### 就绪门与独立心跳审核

只读审核当时的`NetworkRecoveryLoop/NetworkRecoveryGuard/NetworkAndroidPlatform`及`NetworkRecoveryGuardTest`，副本冻结于`research/d31/staging/network-ready-review-20260912-094046-601/`。

已确认保留的正确合同：

- `recoveryReady()`只在跨boot恢复前调用；生产boot读取仍通过真实UUID格式门，原任务boot及期限仍与Journal严格匹配。没有把未知boot当新boot，也没有重建原确认窗口。
- 就绪条件是`sys.boot_completed=1`且独立有界get返回明确ENABLED或DISABLED。它没有在无租约状态调用依赖task现场的`readWifiEnabled()`，也没有写网络设置或修改原事务日志。
- 真正recover仍走原维护租约、调用回执核验、实际前像读回及严格恢复分支；recover返回NEEDS_ATTENTION后仍退出，没有将Binder效果未知改为通用重试。
- Heartbeat初次同步写在调度器启动之前；之后单线程每250毫秒写入，主恢复线程阻塞读取不再阻塞正常心跳。首个普通写异常被保留供check读取。正常控制流中try-with-resources关闭心跳后才释放guard.lock，shutdownNow后最多等待两秒；未终止仅记录提示，最终独立guard命令退出仍是线程收尾的最后保障，不能声称所有不可中断文件I/O都能在两秒内结束。

此次仍发现两项需主线补齐：

1. **P2：就绪读取后的心跳失败检查缺口。** Loop仅在每轮开始调用host.heartbeat；如果四秒就绪读取期间心跳writer失败，检查返回true后没有再次check便进入recover。新增隔离负对照注入这个时序，恢复仍执行一次并返回ROLLED_BACK。建议在耗时就绪探测返回后、进入recover之前再次检查心跳及中断；主线新增回归，不能只测试直接调用Heartbeat.check能看到失败。
2. **P2：150秒并非当前实现的严格总预算。** readiness仍调用固定四秒上限的invoke，false分支还会先pause再在下一轮检查预算。注入四秒实际读取耗时及250毫秒轮询后，负对照在153000毫秒才返回GUARD_BUDGET_EXHAUSTED。现有就绪测试将探测视为零耗时，没有覆盖边界。建议向探测传剩余预算，读取上限不超过剩余时间，探测返回无论真假先重核预算，再决定是否pause或recover。恢复setter和线程清理另有不可抢占或有界收尾时间，文档必须区分“停止新操作的预算”与进程最终退出上限，不宣称整个guard在150秒绝对硬退出。
