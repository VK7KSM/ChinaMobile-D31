# D31卡开机时的以太网救援

## 先看结论

2026年9月6日，故障D31停在开机界面，无法操作桌面，普通ADB无法连接。使用原厂`uptool`以太网管理接口后，电脑成功连上ADB，`shell id`实际返回`uid=0(root)`。不需要先进入Recovery，也不需要在屏幕上打开设置。

**只证明这一台、这一现场的管理通道恢复。整机启动修复尚未完成，不能称为通用一键救砖。** 隔离异常启动脚本并重启后，原厂二层查询仍有有效回复，但ADB连接还未恢复；已暂停设备操作整理本教程。不要把第一次成功扩大解释为每次开机都必然成功。

仅用于自己拥有或获准维修的D31。脚本必须指定目标有线MAC，不广播、不扫描其他设备。原始响应和系统日志可能含设备信息，不要直接上传到公开仓库或论坛。

## 适用条件

- D31仍通电、有线网卡和原厂`/system/bin/uptool`服务仍工作。卡桌面不一定影响该服务，但服务没起来时无法使用。
- Windows电脑与D31位于同一个有线二层网络。通常是接入同一路由器的LAN口或同一交换机，不能经过访客隔离、不同VLAN或普通三层VPN。
- 电脑安装Python 3.8或更新版本、官方Npcap和Android平台工具。脚本仅使用Python标准库，不需要安装Scapy。
- 已核实D31的有线MAC和有线IPv4。可从路由器租约、设备标签及已知记录交叉核对；有多台D31时不要凭型号随便选择。以太网查询按MAC寻址，恢复后的ADB仍需要正确IP。

官方下载：[Npcap](https://npcap.com/#download)、[Python](https://www.python.org/downloads/windows/)、[Android平台工具](https://developer.android.com/tools/releases/platform-tools)。此次实测Npcap为1.88，安装器数字签名有效，签发者为Nmap Software LLC。安装驱动可能短暂影响电脑网络。不要下载来历不明的驱动合集。

## 电脑准备

1. 下载并解压[项目ZIP](https://github.com/VK7KSM/ChinaMobile-D31/archive/refs/heads/main.zip)。救援脚本位于`tools/recovery`，不是刷机工具EXE的一部分。
2. 安装Npcap和Python；解压Android平台工具，记下`adb.exe`的完整路径。
3. 以管理员身份打开PowerShell，进入项目的`tools/recovery`目录。下面命令的变量均在同一个PowerShell窗口中使用。
4. 查看驱动及网卡：

```powershell
Get-Service npcap
Get-NetAdapter -Physical | Format-Table ifIndex, Name, Status, MacAddress
```

Npcap应为`Running`。选择实际连接D31所在局域网、状态为`Up`的以太网适配器，不选Wi-Fi、WARP或虚拟网卡。运行下面命令并按提示填写：

```powershell
$nicIndex = [int](Read-Host '请输入上面有线网卡的ifIndex')
$nic = Get-NetAdapter -InterfaceIndex $nicIndex
if ($nic.Status -ne 'Up') { throw '所选网卡未连接，停止' }
$adapter = '\Device\NPF_' + ([guid]$nic.InterfaceGuid).ToString('B')
$sourceMac = $nic.MacAddress
$targetMac = Read-Host '请输入已核实的D31有线MAC，不是电脑MAC'
$ip = Read-Host '请输入该D31的有线IPv4'
$adb = (Resolve-Path -LiteralPath (Read-Host '请输入adb.exe完整路径，不加引号')).Path
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
```

需要辅助核对邻居记录时，可执行`Get-NetNeighbor -InterfaceIndex $nicIndex -AddressFamily IPv4`。记录可能过期或不完整，不能仅凭一条邻居记录确定设备归属。

## 第一步：只查询目标设备

```powershell
python .\query_uptool.py --adapter $adapter --source $sourceMac --target $targetMac --output ".\query-$stamp"
```

脚本发送一帧单播查询，等待8秒；输出目录必须是新目录，不覆盖之前的记录。允许继续的结果是`responses`中出现：

```json
{
  "action": "0x0102",
  "checksum_valid": true,
  "device_info_response": true
}
```

实测返回载荷为1448字节。长度本身不是成功条件，必须核对动作和校验。只有`request_sent=true`、只有自己发出的帧，或空的`responses`，均不能算查询成功。无回复时核对网卡、MAC和二层连接，保留输出，不继续盲发命令。

这里“只读”指不写配置和系统文件；原厂进程仍会更新临时查询状态。MD5字段只是协议校验，不是身份认证或安全加密。

## 第二步：临时恢复ADB

确认第一步成功后：

```powershell
python .\restore_adbd_uptool.py --adapter $adapter --source $sourceMac --target $targetMac --output ".\restore-$stamp"
& $adb -P 5042 connect "${ip}:5555"
& $adb -P 5042 -s "${ip}:5555" shell id
```

恢复脚本内部只包含下面这条固定命令，不提供任意远程命令输入：

```sh
test "$(id -u)" = 0 && setprop service.adb.tcp.port 5555 && setprop ctl.start adbd
```

- 只修改临时端口属性并启动已有adbd，不设置`persist.*`，不关闭认证，不重启整机，不修改防火墙或应用。
- 此动作没有直接回包，`responses=[]`不等于失败。以ADB实际连接和shell返回为准。此次成功现场返回root，其他固件不能据此保证同样权限。
- **5042是电脑ADB服务器端口；5555是D31监听端口。** 不使用默认5037，不停止其他项目的5038或5041，也不运行`taskkill /IM adb.exe`。
- 如果只有本目标存在旧`offline`记录，可先执行`& $adb -P 5042 disconnect "${ip}:5555"`，再连接一次。电脑端断开旧连接不能修复设备端未监听或防火墙阻断。
- 若adbd已经运行在另一端口，`ctl.start`未必会重新打开监听；若显示`unauthorized`，本脚本不绕过认证；若启动守护随后关闭adbd，本脚本也不保证持久连接。
- 原厂协议会去重会话。此实测脚本使用固定会话号2，同一原厂服务生命周期内再次发送可能被忽略。不要循环执行或自行拼接恢复出厂、升级、任意命令。

## 第三步：保存现场，再决定修什么

ADB已连接后先运行：

```powershell
$evidence = (New-Item -ItemType Directory -Path ".\device-$stamp").FullName
& $adb -P 5042 -s "${ip}:5555" shell getprop sys.boot_completed
& $adb -P 5042 -s "${ip}:5555" shell getprop init.svc.bootanim
& $adb -P 5042 -s "${ip}:5555" shell pm path com.starnet.nexui
& $adb -P 5042 -s "${ip}:5555" logcat -d -b all -v threadtime | Out-File -Encoding utf8 "$evidence\logcat.txt"
& $adb -P 5042 -s "${ip}:5555" pull /data/local/d31-patches/apply-home-patch.sh "$evidence\apply-home-patch.sh"
& $adb -P 5042 -s "${ip}:5555" pull /data/local/d31-patches/home-patch.log "$evidence\home-patch.log"
```

若拉取返回权限错误或文件不存在，应记录失败，不把它当成已经备份。日志只保存在自己电脑上，可能含SIP配置、号码和设备信息，分享前先脱敏。

本次故障现场的已确认事实：

- 包管理扫描和AMS就绪事件已出现，但`sys.boot_completed`为空、开机动画仍运行，活动列表没有桌面任务。
- `pm path com.starnet.nexui`为空，包登记表中没有Nexui。原厂APK仍存在，SHA-256与早期原件一致，并非APK被物理删除。
- 现场v9启动脚本SHA-256为`786AEAB0B906BFFA723FF8C87F2EDDDD9C184E4F60BDB57881D492FD08B22C4C`，在应用扫描前绑定TLS库，随后因Nexui路径缺失超时并回滚。
- 系统历史日志记录过`System package com.starnet.nexui no longer exists; wiping its data`，私有目录已为空。恢复ADB不会自动恢复已经被系统清理的数据。

为验证启动脚本是否导致故障，维护者已经把这台设备的v9脚本改为带时间戳的隔离名，使原启动钩子不再执行它，然后重启了一次。**这一步尚未通过整机恢复验收，不作为读者直接照抄的通用修复命令。** 脚本、原厂APK和其他应用没有删除；下一步需继续取得本次启动的日志。不要直接用修改过的APK覆盖`/system`，不要清除应用登记数据库，更不要把别人的分区备份写进自己的D31。

## Recovery与卡刷的边界

有ADB时可以请求`adb reboot recovery`，但本次没有执行该命令，也没有验收卡刷。当前尚无适用于各批次移动定制D31的已确认物理按键组合。未进入Recovery时，把ZIP放入TF卡或U盘并不代表会自动执行；Android启动窗口还可能遮住升级确认框并吞掉键盘和鼠标输入。

只有实际进入Recovery、确认菜单和本机备份匹配，才使用[README中的备份恢复流程](../README.md#刷机失败变砖抢救教程)。该完整备份恢复路线可能清空用户数据，与本页不清数据的临时ADB恢复不同。

## 开发记录与安全边界

协议来自本地归档原厂`uptool`的静态分析：`EtherType=0x9974`，设备查询动作`0x0101`、回复`0x0102`，固定ADB恢复使用命令动作`0x0301`。不是TCP/UDP端口，也不是8765状态探针的命令功能。原厂服务不依赖Android的`BOOT_COMPLETED`，这是卡开机时仍有机会恢复管理的原因。

本次查询收到校验正确的回复，随后固定命令恢复root ADB，证明这台设备的原厂二层管理接口可达。这同时提示：普通IP防火墙不能等同于已经封堵原始以太网管理通道。维修期间只接可信局域网；本次不禁用它，以免失去目前可用的救援入口，后续安全收尾需单独处理。

公开目录只包含定向查询和固定ADB启动脚本、离线测试及校验清单；不含账号、MAC、IP、令牌、原始设备响应或刷机工具源码。本地详细开发记录见工作区`d31.md`第38.215节起。
