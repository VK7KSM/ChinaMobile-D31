## 2026-09-19 增量同步：1.34.22-alarm-bounded-loop

- 本次同步 `media/AlarmWaveform.java`、`media/AndroidAlarm.java` 及新增单元测试 `media/AlarmLoopCountTest.java`，来源为本次构建生成的完整版与测试变体源码，与 `app/src` 逐字节一致，`source-files.json` 对应三条记录已更新。
- 改动原因：`AndroidAlarm` 原先用 `setLoopPoints(0, samples.length, -1)` 让警报音无限循环，停止完全依赖上层 `AlarmTasks` 的定时器。定时器一旦失效（进程被冻结、Handler 队列卡死、异常路径漏掉 `removeCallbacks`），原生层没有任何兜底，设备会一直响。
- 新增纯函数 `AlarmWaveform.loopMs(frames)` 与 `AlarmWaveform.loopCount(durationMs, loopMs)`：循环次数按时长向上取整，宁可多播一个片段也不截断；任何输入都返回有限正数，不会返回 `-1`（AudioTrack 的无限循环值）。循环片段固定 1.4 秒，10 秒警报取 8 次。
- 定时长警报（`AlarmTasks.DURATION_MS`）在起播时一次装填。不定时长警报（丢失模式 `start(0)`，30 秒发声、10 秒静音循环）按单段发声时长 `REPEAT_BURST_MS` 取 22 次，并在每次恢复播放前重新装填；调度器失效时发声最多再持续约 31 秒即自行结束。恢复播放前先把播放头退回起点，避免静态轨播完预算后只重设循环点仍然无声。
- 新增两项单元测试：一项覆盖取整不截断且余量不超过一个片段，一项断言任何输入下返回值有限且不等于 `-1`，并覆盖片段长度非法时拒绝。
- 循环次数的语义与 `AudioTrack.setLoopPoints` 第三参数一致：它是「再重复几遍」，0 表示不循环（片段仍播放一遍），-1 表示无限循环，总播放遍数为返回值加一。因此 `loopCount` 按总遍数向上取整后减一，10 秒警报返回 7（总共 8 段 11.2 秒），30 秒发声段返回 21（总共 22 段 30.8 秒）。评审指出首版少减了一，与网关和 D22 的口径不一致，已修正，三端现已一致。
- 恢复播放前退回播放头：优先 `setPlaybackHeadPosition(0)`，被拒时回退到静态轨重播的官方接口 `reloadStaticData()`，两者都失败才记警告继续。
- 构建命令与签名约定不变；本次制品为完整版 versionCode 202、基础版 201，正式制品未随源码入库。

### 设备分享链接二维码

服务端生成管理链接并经既有的核心→应用通道下发，设备只负责画成二维码全屏显示，全程不读设备令牌、不向服务端索取链接。核心侧 `ShareLinkTasks` 判定与记账，`ShareLinkPayload` 校验载荷（链接须 `https://`、有效期须未来、显示时长夹到 15–300 秒、含 `password`/`token` 等字段一律拒收）。窗口 `ShareLinkActivity` 在独立进程 `:sharelink`，只有完整版打包。结束原因经应用内 IPC 回报给 `:visual` 的 `ShareLinkWindow`，核心按轮次取——**没有在 uid 0 那侧新开受理入口**。

回执套既有任务状态机，且**显示之前必须先发 `claimed`**：服务端对不在迁移表里的回执是静默丢弃，HTTP 仍是 200、`ok` 仍是 true，只有回体里的 `task.state` 才说明采没采纳。因此采纳判定按回读状态，不一致就补发缺的那一步而非重发同一条。语义值放 `result.share_link.outcome`，`running -> expired` 不在迁移表里，所以到期终态是 `success` 配 `outcome: expired`。

### 两类移植缺陷，方向相反

- **参考实现里缺少的**：D22 系统较新，不需要重写 `onSetSSLParameters`，源码里没有这段，照搬必然漏。D31 是 API 23，Java-WebSocket 默认实现会调 API 24 的 `SSLParameters.setEndpointIdentificationAlgorithm`，抛 `NoSuchMethodError` 打死整个应用进程，界面只显示「已停止运行」。已按本项目 `AdbSessions` 的写法自行完成握手并校验域名，且赶在把会话令牌放进 `Authorization` 头之前验完。新增 `WebSocketApiLevelAuditTest` 扫编译产物，任何 `WebSocketClient` 子类未重写该方法即失败。
- **参考实现里有、但目标平台不支持**：`CompletableFuture` 是 API 24 的类，D22 用它等 SDP 回调，照抄后在 D31 上抛 `NoClassDefFoundError`。已改用 `CountDownLatch` 配 `AtomicReference`。Lint 的 `NewApi` 本可抓到，但它默认不在 `lintVital` 的致命集里，因此 `app/build.gradle` 增加 `fatal 'NewApi'`，并实测确认生效（临时塞入违规调用后 `lintVitalFullRelease` 确实失败）。**发布前必须跑 `lintFullRelease`，不能只跑 `lintVital`。**

### 会话锁与 WebSocket 关闭锁的反向锁序

两条线程按相反顺序各持一把锁互等：一条持会话锁去调 `websocket.close()`，另一条持 WebSocket 关闭锁从 `onClose` 回调进来要会话锁。现象不是报错而是整条会话卡住、上报跟着停，进程还活着、`last_error` 为空。D31 共四处：`AdbSessions.Session.finish`、`AdbSessions.open`/`close`、`DesktopSession.stop`/`shutdown`/`start`、`DesktopSession.checkReady`（经 `fail` 隔两跳），另有 `AppMediaService.onDestroy` 在主线程握类锁关连接的 ANR 风险。改法统一为锁里只翻状态、取引用，关闭动作放到锁外；包装方法不再握锁进去；`snapshot()` 改为只读 volatile，使会话侧阻塞不扩散。

新增 `WebSocketLockOrderAuditTest`：扫字节码，按 `monitorenter`/`monitorexit` 计数判断持锁，**先按调用图算出所有能传递地走到 `close` 的方法**再查持锁调用。两个方向都要避开——只看方法自身字节码会漏掉隔跳的（`checkReady` 即如此）；把 `invokedynamic` 当调用边则会因 lambda 产生大批误报，故只跟 182/183/184/185。范围刻意只查 `close` 不查 `send`：`close` 与 `onClose` 投递同一把锁，是已证实的永久死锁；`send` 走发送队列，消费它的写线程不需要会话锁，构不成环。已知 `PhotoAlarmSocket.send` 属后者，**未改代码，只在现场留注释**说明缘由与排查线索。

本次同步 17 个文件：新增 1 个（`ProxyActivity`），修改 16 个。来源仍为本次构建生成的受控副本，同步前逐字核对与 `app/src` 一致，统一 LF 入库。

- **1.34.32（versionCode 222，`1.34.32-proxy-client`）**：所有者看过 v2rayNG 与 Clash Verge 后否掉了原先的四个操作按钮——那不是代理客户端。改为 `ProxyActivity` 三页：首页（连接/断开开关、当前节点与延迟、订阅信息、走代理的应用、流量与核心版本）、代理页（`AUTO` 加节点列表，每行实测延迟，点行切换，全部测速）、订阅页（版本/校验值/时间/节点数、更新订阅、移除模块）。界面不自己算状态，全部取核心返回的总览，每 5 秒刷新。

  骨架相应扩展：`external-controller` 绑 `127.0.0.1:17992` 加随机口令（存 `state.json`，目录 0700），`PROXY` 手选组 `[AUTO, 节点…]`、`AUTO` 为 url-test 组，加 `dns` 段与 `tun`（`auto-route: false`、`dns-hijack any:53`）。节点段里与 `AUTO`/`PROXY` 同名的一律拒收，否则手选组会指向自己。每次启动都从 `proxies.yaml` 加本机状态重新生成 `current.yaml`。

  **启用 = 起核心 + 建 TUN + 核心自己下按 uid 的策略路由**（`ip rule add uidrange <uid> lookup 2022 prio 9000`）。停止先撤规则再停进程；测速在核心未跑时起一个不建 TUN 的临时实例；切换节点经控制口写入后读回 `now` 核对，不一致报失败而不是假装切了。

  同版修正一处自己的缺陷：「下载并启用」在设备已有配置时仍去服务端要一份，而该接口当时尚不存在，于是弹出「请先登录」。正确逻辑是已配置直接启动，未配置才取。

- **1.34.33（224，`1.34.33-proxy-apps-local`）**：分流名单本机可改（首页「选择应用」多选，列可启动应用，管理程序永不出现）。接服务端第 3 步合同：新任务 `select_proxy_node` 与 `set_proxy_apps`，回执带设备回读的 `selected` / `apps`，其余类型回执仍恰好三键；上报新增 `proxy_nodes` 与 `installed_apps`（后者只在清单摘要变化时带，服务端按「字段缺席 = 保留既有」处理）。向服务端取配置的 `request_id` 9 分钟内复用，配置成功后才换新——换编号会触发限频并作废上一刻刚拿到的令牌，表现就是反复点、反复失败。

- **1.34.34（226，`1.34.34-proxy-apps-report`）**：上报生效中的 `proxy_apps`，让面板显示的名单与设备实际一致。同时把「禁止走代理」的判据从整个 `net.elfradio.` 命名空间收窄到管理程序本身（精确相等或 `<包名>.` 开头）。**这个收窄是必需的**：该命名空间里还有 Zello 守护、SIP 短信客户端和系统支持组件，都是普通应用；服务端当时对名单里出现该前缀是拒整条上报，使用者勾一下守护就会让每一轮遥测被拒，比一次性失联更糟。我自己也犯过同样的错——`installed_apps` 原本也按整命名空间排除，后果更隐蔽：不报错、不失联，只是面板列表里静静少三项。

- **1.34.35（228，`1.34.35-proxy-bearer-token`）**：一次性下载令牌从查询串挪进 `Authorization: Bearer`。查询串会进各种访问日志，令牌不该留在那里。`ProxyDownload.fetch` 摘取时不依赖参数顺序，只剩令牌一项时连问号一并去掉；`validate` 同时接受带令牌与只有 `device_id` 两种形状。服务端读到 Bearer 即以它为准、不再拿查询串兜底，两种形状长期都收。
